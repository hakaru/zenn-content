## きっかけはDexedとMSFA

DX7のソフトウェア再実装で最も有名なのは **Dexed** というVSTプラグインだと思う。無料で使えるDX7エミュレーターで、DAWユーザーなら知ってる人も多いはず。

Dexedの心臓部は、Googleのエンジニア Raph Levien が2012年に書いた **music-synthesizer-for-android（MSFA）** というC++エンジン。もともとはAndroid向けに作られたもので、DX7の実機をMIDI経由で測定し、波形をビットレベルで一致させるという執念のプロジェクトだった。

https://github.com/google/music-synthesizer-for-android

MSFAのコードを読んで衝撃を受けた。たった2000行くらいのC++で、DX7の全32アルゴリズム、エンベロープ、LFO、フィードバックが動いてる。しかもApache 2.0ライセンス。

「これをSwiftで、Appleプラットフォーム向けに書き直したい」。それが始まり。

## FM音源の仕組み

FM音源の原理自体はシンプルで、サイン波の周波数を別のサイン波で揺らす（変調する）と倍音が生まれる。DX7はこの「オペレーター」を6個持っていて、接続パターン（アルゴリズム）が32種類ある。

```
例: アルゴリズム1
OP6 → OP5 → OP4 → OP3 → OP2 → OP1 → 出力
（直列6段。OP6のフィードバックあり）

例: アルゴリズム32
OP6 ─┐
OP5 ─┤
OP4 ─┼→ 出力
OP3 ─┤
OP2 ─┤
OP1 ─┘
（全キャリア。加算合成に近い）
```

原理は単純なんだけど、問題は「DX7の音」を出すには原理の理解だけじゃ足りないということ。実機のOPSチップ（YM21280）がどういう精度で演算してるか、エンベロープのカーブがどうなってるか、フィードバックの計算順序はどうか——そういう細部が全部音に出る。

## MSFAから学んだこと

MSFAのコードを読み込んで、DX7の内部実装が見えてきた。

### 対数ドメインの演算

DX7のOPSチップは、ゲイン計算を**対数領域**で行う。掛け算を足し算に変換できるので、1980年代のハードウェアでも高速に処理できた。MSFAはこれを忠実に再現していて、周波数もゲインもすべてQ24固定小数点の対数表現で持っている。

### サイン波テーブル

1024エントリのルックアップテーブルに線形補間をかける。`sin()`を毎サンプル呼ぶのではなく、テーブル参照で高速化。MSFAでは差分ベースのLUTも用意されていて、精度と速度のトレードオフを選べる。

### エンベロープの非線形性

DX7のエンベロープは単純なADSRじゃない。アタックは非線形カーブ（速く立ち上がって後半ゆっくり）、ディケイは線形減衰。レート値（0〜99）は内部で量子化されて、`(4 + (qrate & 3)) << (8 + (qrate >> 2))` みたいな式でインクリメント値に変換される。

この辺、仕様書だけ読んでも分からない。MSFAのコードとDexedのwikiを突き合わせて、やっと理解できた。

### 32アルゴリズムのビットフラグ表現

MSFAの最もエレガントな部分がここ。32種類のオペレーター接続パターンを、1オペレーターあたり1バイトのフラグで表現してる。

```
ビット0-1: 出力先バス（0=メイン, 1=バス1, 2=バス2）
ビット2:   加算フラグ
ビット4-5: 入力元バス
ビット6-7: フィードバック
```

6オペレーター × 1バイト = たった6バイトで1アルゴリズムが定義できる。32アルゴリズム全部でも192バイト。この設計のおかげで、アルゴリズムごとに分岐を書く必要がなく、1つのジェネリックなループで全パターンを処理できる。

自分のSwift実装でもこの設計をそのまま採用した。

## Swiftで再実装する

MSFAを「読んで理解した」のと「Swiftで書き直す」のは全く別の作業だった。

### 固定小数点演算

DX7は整数演算で動いている。Swiftでも`Int32`のQ24固定小数点で書いた。

```swift
// 位相アキュムレータ: Q24。1周期 = 2^24
var phase: Int32 = 0
let phaseIncrement: Int32  // freq / sampleRate * (1 << 24)

// ゲイン適用: 64bit中間値でオーバーフロー防止
let output = Int32((Int64(sineValue) &* Int64(gain)) >> 24)
```

Swiftの`Int32`はオーバーフローでクラッシュするので、意図的なラップアラウンドには`&*`（オーバーフロー演算子）が必要。C言語だと暗黙にラップするから、MSFAのコードをそのまま移植すると落ちる。ここで何度もハマった。

### サインテーブルの生成

MSFAは静的テーブルだけど、自分は実行時に回転行列の漸化式で生成するようにした。

```swift
// 回転行列でsin/cosを逐次生成（累積誤差が小さい）
// [cos(θ+dθ)]   [cos(dθ) -sin(dθ)] [cos(θ)]
// [sin(θ+dθ)] = [sin(dθ)  cos(dθ)] [sin(θ)]
```

直接`sin()`を1024回呼ぶより数値的に安定する。テーブルサイズは2048エントリ（値+差分のインターリーブ）、14ビット線形補間。

### exp2テーブルの罠

対数ドメインから線形ドメインへの変換に使うexp2テーブル。1024エントリのQ30テーブルを引いて、オクターブ分のシフトを加える——という処理なんだけど、Int32のオーバーフロー挙動がC言語とSwiftで違う。

MSFAのCコードでは `int` のオーバーフローが「たまたま正しい結果」になるケースがあって、Swiftでは`&*`と`&+`を正確に配置しないと値がズレる。ここは1バイトのズレを追い詰めるのに丸2日かかった。

### エンベロープジェネレータ

DX7のエンベロープ再現は、このプロジェクトで一番時間を使った部分かもしれない。

```swift
// アタック: 非線形（レベルが高いほど遅くなる）
let step = ((17 << 24 - level) >> 24) &* inc

// ディケイ/リリース: 線形減衰
level -= inc
```

アタックカーブの `17 << 24 - level` という式。これがDX7特有の「速く立ち上がって後半なめらかに収束する」カーブを生む。数式自体は短いけど、ここに至るまでにMSFAのコード、Dexedのwiki、dx7のサービスマニュアルを何度も往復した。

### リアルタイムオーディオのスレッド制約

オーディオレンダリングスレッドではメモリアロケーション禁止。Swiftで普通にコードを書くとArrayの生成やクロージャのキャプチャでヒープアロケーションが発生する。

対策として:
- 128ボイス分のバッファを起動時に全部確保
- パラメータの受け渡しはロックフリーのSPSCリング（`Synchronization.Atomic`ベース）
- `SynthParamSnapshot`は固定サイズのタプルで持つ（Arrayを使うとdrop時にdeallocが走る）

```swift
// ❌ Arrayはヒープアロケーションが発生する
var slots: [SlotSnapshot]

// ✅ タプルなら値型でスタックに収まる
var slots: (SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot)
```

見た目は最悪だけど、オーディオスレッドの安全性には代えられない。

## ビット精度の検証

「DX7の音が出る」と言うからには証明が必要。MSFAのCコードをテスト専用ターゲットとして組み込んで、サンプル単位で波形を比較するテストを書いた。

```swift
@Test func voiceOutputMatchesReference() {
    // 同じパッチ、同じノートで両エンジンをレンダリング
    let swiftOutput = swiftVoice.renderBlock(samples: 64)
    let refOutput = dx7ref_voice_render(patch, note, 64)

    // Int32レベルで完全一致を要求
    for i in 0..<64 {
        #expect(swiftOutput[i] == refOutput[i])
    }
}
```

このテストで何十個もバグを見つけた。レートスケーリングの量子化式が1ビットずれてる、exp2のオーバーフロー方向が逆、出力のスケーリング除数が2^28じゃなくて2^25だった、など。仕様書を読んだだけでは絶対に気づかないレベルの話。

MSFAのCコードはApache 2.0ライセンスなので、テスト用途のリファレンス実装として組み込んでいる。プロダクションビルドには含まれない。

## SysExパッチの読み込み

DX7のパッチは **SysEx（System Exclusive）** というMIDIメッセージ形式で保存される。32音色分のバルクダンプが4104バイト。1音色あたり128バイトで、6オペレーター × 17バイト + グローバルパラメータ26バイト。

ビットパッキングが凄まじくて、たとえばデチューンは `(byte[offset+12] >> 3) & 0x0F` みたいに1バイトの中にフラグと値が混在してる。1980年代のメモリ節約の知恵。

DX7のファクトリーROM（ROM1A〜4B）、VRC（Voice ROM Cartridge）、DX7II用パッチ、Grey Matter E!拡張パッチをバンドルしてる。ネットに転がってる`.syx`ファイルもそのまま読める。

## マルチティンバー

DX7は1台1音色だけど、TX816（DX7のモジュール版TF1を8台ラックに詰めたやつ）風のマルチティンバーも実装した。

| モード | スロット数 | 1スロットのボイス数 |
|:---:|:---:|:---:|
| Single | 1 | 16 |
| Dual | 2 | 8 |
| Split | 2 | 8 |
| TX816 | 8 | 2 |

実機のTX816はTF1が1枚あたり16ボイス、フル構成で128ボイスのモンスター。M2DX-Coreは全体で16ボイスの制約があるので、TX816モードだと8音色×2ボイスに分割される。実機の再現ではなく、限られたリソースでマルチティンバーをどう割り振るかという設計判断。

## Swift 6 Strict Concurrency

Swift 6のStrict Concurrency Modeをフルで使ってる。UIスレッドとオーディオスレッドの間でデータ競合が起きないことをコンパイラが保証してくれる。

パラメータの受け渡しは2種類のロックフリーリングバッファ:

- `SnapshotRing` — 「最新値だけ欲しい」用。UIがパラメータを変更するたびにpush、オーディオスレッドは最新のスナップショットだけpopLatest。中間値は捨てる
- `SPSCRing` — MIDIイベント用FIFO。ノートオン/オフは順序が大事なので全部保持

どちらも`Synchronization.Atomic`のacquire/releaseオーダリングで実装。ミューテックスもCASループも使っていない。

## 苦労した話

一番きつかったのは「音が微妙に違う」の原因特定。波形を目視で比較しても分からないレベルの差異を、サンプル単位のInt32比較テストで炙り出す作業。

exp2テーブルの1ビットのズレが、エンベロープを通すと数dBの音量差になり、フィードバックを通すと音色が全く変わる。FM音源はパラメータの微小な変化に対して非線形に反応するので、「だいたい合ってる」は通用しない。

あとSwiftの`Int32`オーバーフロー。Cでは未定義動作だけど実質ラップアラウンドするコードが、Swiftでは即クラッシュ。MSFAのコードを1行ずつ読んで、オーバーフローが起きうる箇所を全部`&+`/`&*`に置き換える作業は地味にしんどかった。

## おわりに

MSFAのコードを読み始めてからM2DX-Coreが107テスト全パスするまで、約1年かかった。FM音源の原理は教科書で学べるけど、「DX7の音」を出すには実機チップの挙動を1ビット単位で追いかける必要があった。

Raph Levienが実機を192kHz/24bitで録音して波形を解析した執念、Pascal GauthierがDexedでMark Iエンジン（実機の不完全さまで再現するモード）を追加した哲学。その積み重ねの上に自分のSwift実装がある。

FM音源に興味がある人は、MSFAのコードを読むことをおすすめする。2000行で6オペレーターFMシンセが動く、教科書的に美しいコードベースだと思う。
