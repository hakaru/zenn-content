## 録音アプリなのに音が「のっぺり」する問題

1TakeというiOS録音アプリを作っている。プリセットに「Studio（LA-2A風）」「Studio+（1176風）」と書いてあるのに、中身はAppleの`kAudioUnitSubType_DynamicsProcessor`——つまりただのデジタルコンプレッサーだった。

パラメータをいじればそれっぽい設定にはなる。でもLA-2Aのあの「音が前に出てくる感じ」や、1176の「叩いた瞬間にギュッと締まる感じ」は、パラメータの数値じゃなくて回路の非線形性から来ている。

ユーザーに嘘をついてる気分だった。v1.5.0で本物を作ることにした。

## LA-2Aって何がすごいのか

1960年代にTeletronixが作ったオプトコンプレッサー。中にフォトセル（光依存抵抗器）が入っていて、信号が大きくなるとLEDが光り、その光で抵抗値が変わって音量が下がる。

何がユニークかというと、このフォトセルの応答が非線形なこと。

- 圧縮が浅いとき → リリースが速い
- 圧縮が深いとき → リリースがめちゃくちゃ遅い

人間の耳にはこれが「自然なレベリング」に聞こえる。ボーカルに使うと、声が前に張り付いてくる。アコースティックギターのアルペジオが粒立つ。デジタルコンプの「均一に潰される感じ」とは全然違う。

もうひとつ。LA-2Aは回路全体に真空管が使われていて、信号が通るだけで偶数次倍音が足される。これが「温かい音」の正体。

## 1176の性格

UREI（のちにUniversal Audio）が1967年に出したFETコンプレッサー。LA-2Aとは真逆の性格。

- アタックが異常に速い（最速20μs）
- 入力が大きいほどアタックがさらに速くなる
- FETの非線形特性で奇数次倍音が出る

ドラムのスネアに1176をかけると「パツン」と前に出てくる。エレキギターのリフがザクザク切れる。LA-2Aが「優しく包む」なら1176は「殴って整える」。

有名な「全押し」モード（All Buttons In）では4つのレシオボタンを全部押し込む。本来の設計意図にない使い方だけど、結果的にRatio 20:1くらいの強烈な圧縮になって、独特の歪みが乗る。ドラムのルームマイクでよく使われる。

## iPhoneで再現できるのか

正直、最初は懐疑的だった。アナログ回路の「味」をデジタルで出すなんて、プラグインメーカーが何十年もかけてやってきた仕事だ。

でも実際にやってみると、iPhoneのCPUパワーは十分すぎた。サンプル単位（48kHzなら1秒に48,000回）でDSP処理を回しても、CPU負荷は1%以下。A15以降のチップなら余裕。

問題はCPUじゃなくて、リアルタイムオーディオのスレッド制約だった。

## レンダーコールバックでやっていいこと、だめなこと

iOSのオーディオ処理はレンダーコールバック（`internalRenderBlock`）の中で行う。このコールバックはリアルタイムスレッドで呼ばれる。

ここでやっちゃだめなこと：

- メモリ確保（`malloc`）
- ロック取得（`NSLock`、`os_unfair_lock`）
- Objective-Cのメッセージ送信
- ファイルI/O

最初の実装ではうっかり`NSLock`を使ってしまい、Codexのレビューで指摘された。ロックの待ち時間でオーディオバッファが間に合わなくなると、プチプチとノイズが出る。

修正は単純で、設定値をSwiftの値型（`struct`）にして、メインスレッドから書き換えてもレンダースレッドはコピーを読むだけにした。arm64ではstructの代入がアトミックなので、中途半端な状態を読むことはない。

## DSPコードの中身

実装は`BaseCompressorDSP.swift`の140行に収まった。コアのループはこんな感じ：

```swift
for i in 0..<frameCount {
    // サイドチェーン検波
    let sidechainSample = max(abs(left[i]), abs(right[i]))
    
    // エンベロープフォロワー
    if target > state.envelope {
        // アタック
        state.envelope = target + attackCoef * (state.envelope - target)
    } else {
        // リリース（LA-2Aは圧縮量で変わる）
        var releaseCoef = releaseCoefBase
        if model == .opto {
            let grAmount = 1.0 - state.gainReduction
            releaseCoef = exp(-1.0 / ((releaseTime + grAmount * 2.0) * sampleRate))
        }
        state.envelope = target + releaseCoef * (state.envelope - target)
    }
    
    // ゲインリダクション計算（ソフトニー対応）
    let desiredGR = calculateStaticCurve(inputDB: envDB, settings: settings)
    
    // ハーモニック彩色
    if model == .opto {
        left[i] = tanh(left[i] * 1.2) / 1.2  // LA-2A: 真空管風
    }
    if model == .fet {
        left[i] = left[i] + 0.1 * left[i] * left[i] - 0.01 * left[i] * left[i] * left[i]  // 1176: FET風
    }
}
```

ポイントは3つ。

### 1. 非線形リリース（LA-2Aモデル）

圧縮量（`grAmount`）が大きいほどリリース係数が大きくなる、つまりリリースが遅くなる。これがLA-2A特有の「深く圧縮すると戻りが遅い」挙動を再現している。

普通のコンプレッサーはリリースタイムが固定。LA-2Aは信号に応じて勝手に変わる。だから設定が少なくても音楽的に使える。

### 2. ソフトニー

```swift
// 閾値の前後でなめらかに圧縮が始まる
if knee > 0 && inputDB < threshold + knee / 2.0 {
    let x = inputDB - threshold + knee / 2.0
    let grDB = (1.0 - 1.0 / ratio) * (x * x / (2.0 * knee))
    return -grDB
}
```

ハードニー（knee=0）だとThresholdを境にカクっと圧縮が始まる。ソフトニーは二次関数でなめらかにつなぐ。LA-2A風のStudioプリセットはknee=24dBで、ほとんど気づかないくらい自然にかかる。

### 3. ウェーブシェーピング

LA-2Aモデルでは`tanh`、1176モデルでは多項式（`x + 0.1x² - 0.01x³`）でハーモニクスを加えている。

`tanh`は入力が大きいほど飽和する。真空管のソフトクリッピングに近い。結果として偶数次倍音が足される。

多項式の方は奇数次倍音が出る。FETの非対称な特性をざっくり模倣したもの。Wavesとかの本格プラグインはもっと精密なモデルを使ってるけど、録音アプリの用途ならこれで十分キャラクターが出る。

## パラメータの意味

UIには6つのスライダーが並ぶ。それぞれに英語のヒントテキストをつけた。

| パラメータ | 何をするか | 迷ったら |
|-----------|-----------|---------|
| Threshold | 圧縮が始まるレベル | -24dBあたりから始めて、GRメーターが2-3dB振れるところに |
| Ratio | 圧縮の強さ | LA-2A風なら3:1-4:1、1176風なら8:1-12:1 |
| Knee | 圧縮の始まり方 | 0=ハード（パキッと）、24=ソフト（じわっと） |
| Attack | 圧縮の反応速度 | 遅くするとアタックが残ってパンチが出る |
| Release | 圧縮の戻り速度 | LA-2Aモデルは自動で変わるので気にしなくていい |
| Makeup Gain | 圧縮で下がった分を補正 | GRメーターの平均値と同じだけ上げる |

ちなみにAttackとReleaseの「速い」「遅い」は直感と逆になりやすい。数値が小さい＝速いなので注意。

## 2段コンプレッション

1Takeのエフェクトチェーンにはコンプレッサーが2つある。

```
Input → Gate → EQ → Comp1 → Comp2 → Saturation → M/S → Maximizer
```

Comp1（Transparent Compressor）がダイナミクスを整えて、Comp2がキャラクターモデル（LA-2A/1176/VCA）で色付けする。プロのレコーディングスタジオでも、この「整えてから色付け」の2段構成は定番。

実際に弾き語りを録ってみると、Comp1だけだとクリーンだけど味気ない。Comp2だけだと効きがムラになる。両方合わせるとちょうどいい。

## 実装して気づいたこと

UA/Waves/Arturiaのプラグインと比較すると、当然ながら精密さでは負ける。彼らは回路の部品一つ一つをSPICEシミュレーションしている。うちのは「それっぽい非線形性を最小限のDSPで再現する」アプローチ。

でも、iPhone内蔵マイクで練習の録音を録るという用途なら、これで十分以上だと思ってる。「なんかプロっぽい音になった」と感じてもらえれば勝ち。

あと地味に大事だったのが、パラメータごとのヒントテキスト。「Thresholdって何？」の答えがスライダーの真下に書いてある。これだけで初心者の離脱がかなり減るはず。

## 技術的な落とし穴

開発中にハマったことをいくつか。

vDSPの`vDSP_maxv`で波形のピーク値を取ろうとしたら、負の方向に大きい波形で値がおかしくなった。正しくは`vDSP_maxmgv`（絶対値の最大）を使う。レビューで発見されるまで気づかなかった。

RecordingAnalysisに`peakDB`と`avgRMS`フィールドを追加したとき、既存の保存済みJSONとの後方互換が壊れた。`Codable`のデコーダーをカスタムして`decodeIfPresent`でフォールバックを入れた。

NoiseGateやSaturationの設定画面でローカリゼーションキーがない参照をしていて、UIに`"compressor.hint.threshold"`という生のキー文字列が表示されていた。全部ハードコード英語に置き換えた。オーディオ用語は世界共通で英語なので、むしろ日本語に訳さない方が自然。
