バッハのフーガを1小節だけ見せられて「なぜこの音がここにあるの?」と聞かれたとする。

ちゃんと答えはある。「主題（subject）の答唱（answer）が属調で入ってきて、この音は調性的応答（tonal answer）のために半音ぶん補正されたから」みたいに。全部の音に理由がある。作曲家の頭の中にも、対位法の教科書にも、それを生成したアルゴリズムの中にも。

なのに、その理由を保存する場所が、いまの楽譜フォーマットには無い。

## 楽譜は「何が鳴るか」しか書けない

いま音楽データの世界標準はだいたいこの3つ。

- **MusicXML** … 五線譜をどう印刷・描画するか（グラフィック中心）
- **MIDI** … どの鍵盤をいつ・どの強さで押すか（演奏中心）
- **MEI** … 歴史・校訂の解釈や異読を保持する（学術中心）

どれも優秀で、「何が鳴るか」は完璧に書ける。でも「なぜ鳴るか」を書く欄が無い。

これが地味に効いてくるのが、AI やアルゴリズムに作曲させたときで。出力は立派なんだけど、生成の過程はブラックボックス。「なぜここでこの音を補正した?」「なぜこのストレッタ（追迫）の配置を選んだ?」を保存しようとすると、既存フォーマットでは *推論が丸ごと落ちる*。

僕はこれを **Loss of Reasoning（推論の欠落）** と呼んでいる。結果は残るのに、理由が消える。

## 音の Why を書く、という発想 — LOGOS

だったら理由ごと書けるフォーマットを作ればいい、というのが **LOGOS** の出発点。

音楽を「感覚（Pathos）」でも「記号（Graphic）」でもなく、**「論理（Logos）」としてエンコードする**。名前は再帰頭字語になっていて、Logos Organizes Generative Objects and Semantics。つまり素材（Objects）と意味論（Semantics）を分けて編成する、というのがそのまま設計思想になっている。

音符の羅列じゃなくて、各音が「度数」「役割」「緊張度」みたいな理論的属性を持ったオブジェクトとして立ち上がる。で、そのオブジェクトに「なぜここにあるか」という意味論を紐づける。XAI（説明可能なAI）の考え方を、音楽表現に持ち込んだ感じ。

もともとは自分で書いている作曲エンジン **WCC**（バッハ風のフーガを生成するやつ）から出てきた実需だった。エンジンが「調性的応答だからこの音を直した」と判断した、その判断ログを捨てたくなかった。生成の理由を残せる中間表現が欲しい。LOGOS はその理論的中核を切り出したプロジェクト。

## v1.0 まで — 4層で理由を書いた

最初のバージョン（v1.0）は、音楽を4つの独立した層に分けて書く XML フォーマットにした。

- `definitions` … 主題・モチーフなどの素材（音楽の DNA）
- `structure` … それが「いつ・どの声部に・どの調で」出るかの配置図
- `analysis` … 対位法の禁則チェック結果、和声機能、音を補正した理由（**ここが核心**）
- `recommendations` … アルゴリズムが探索した候補と、なぜそれを選び・他を棄てたかのスコア

`analysis` 層が音楽を「ホワイトボックス化」する担当で、`recommendations` 層は *棄却された候補* まで残す。「選ばれなかった道」もデータになる、というのが我ながら気に入っていた。

ここまでは順調で、RNC → RNG → XSD のスキーマ一式、Python の参照実装、平均律クラヴィーア第1巻のコーパス、学会論文のドラフトまで到達した。動くものが揃った。

……で、そこで止まった。

## 54日、止まった

正確に54日、コミットが止まった。

理由は技術的なつまずきじゃなくて、もっと嫌なやつだった。**「ファイルが作れること」と「音楽分析として妥当であること」は、全然別の話だ**と気づいてしまった。

v1.0 は、気づけば「浄書フォーマット」の方向に寄っていた。楽譜を綺麗に構造化することはできる。スキーマも通る。でも、そこに書いた `analysis` が音楽分析として *正しい* かどうかを、何で検証すればいいのか自分でも曖昧だった。検証の基準が無いまま構造だけ立派になっていく。

これは進めるほど不安になるやつで。手が止まった。

## 書くのをやめて、重ねることにした — LOGOS Next

止まったあと、方針を1個ひっくり返した。**新しい楽譜フォーマットを作るのをやめた。**

代わりに、既存のソース（MusicXML / MIDI / リードシート / v1）はそのまま置いておいて、その上に **分析レイヤーだけを重ねる（overlay）**。これが再設計版、**LOGOS Next**。浄書はしない。関係を書く。

軸にしたのはこの問い。

> いつ、何が、何とどう関係し、どの理論と根拠によってそう解釈されるのか。

これを、人間が読めて、プログラムが検証・検索・生成に使える形で書く。同じグラフから3つの顔を出せるようにした。機械が食う semantic graph、人間が書く DSL、そして人間が読む **visual lanes**。

lanes の実際の出力がこれ。ジャズの ii–V–I を3小節ぶん。

```text
Time         m1                        m2                        m3
Harmony      Dm7 / ii7                 G7(b9,no5)                Cmaj7 / Imaj7
Function     predominant ─────────────→dominant ────────────────→tonic
Guide 1                                F4 ──────────────────────→E4
Alternative                            [Db:7]? [g-root-dominant-f
```

同じ時間軸に、レーンが縦に並ぶ。`Harmony` はコード記号（`Dm7`）と度数（`ii7`）の両方。`Function` は機能で、`predominant → dominant → tonic` の解決を矢印で引いている。`Guide 1` はガイドトーンの声部進行（`F4 → E4`、7th が3rd へ落ちるやつ）。

面白いのが一番下の `Alternative`。`G7` は裏コードの `Db7` としても読める、という **別解が `?` つきで併記されている**。どっちが正解、じゃない。両方の読みを、根拠つきで残す。

（余談。lanes のセルは26文字で切っているので、長い別解ははみ出す。実務用の雑さがそのまま出ていて逆に好き。）

6つの基本要素（Anchor / Event / Material / Context / Relation / Claim）とか DSL の文法とか、この裏側はけっこう作り込んだんだけど、全部書くと長いので**入門書のほうで詳述する**。ここでは「重ねる」「関係を書く」「別解を併記する」の3つだけ持って帰ってもらえれば十分。

## スキーマより先に「答え」を決める — gold questions first

もう1個ひっくり返したのが、作る順番。

普通はフォーマット（スキーマ）を先に決めて、そこにデータを流し込む。LOGOS Next は逆にした。**先に「人間が期待する分析の答え」を固定してから、それを返せるかどうかでフォーマットを駆動する**。これを gold questions first と呼んでいる。

やり方はこう。バッハ2例と自作ジャズ2例を選んで、ソース上の正確なアンカー、人間が期待する分析結果、その結果を返すクエリ、そして **競合する解釈と未確定事項** まで先に書く。これが揃ってからカーネルを実装する。「ファイルが作れる」だけでは前に進まないようにした。54日の反省がそのまま設計に入っている。

ここで効いてくるのが2つ。

**Plurality（複数解の併記）**。さっきの裏コードみたいに、一つの現象を複数の理論で読めるとき、勝者を1つに潰さない。全部の読みを残す。

**Evidence（根拠の接地）**。どの主張も「ソースのここが根拠」というアンカーに紐づく。宙に浮いた分析を許さない。

ルールも実行可能な形で12個書いた。同じ「並行完全五度」の検出が、対位法プロファイルでは *禁則（violated）*、ジャズプロファイルでは *容認（exception）* になる。文脈で評価が変わるのを、同じルールで実証できる。この二重評価も、詳しくは本で。

## いまここ — まだ答えは出ていない

で、正直な現在地。

実装フェーズ（Phase 0〜4）は一通り終わっている。カーネル、DSL、プロファイル、12ルール、クエリ API、lanes、アダプタ、全部動く。ジャズ2契約は owner 承認済み（Accepted）、バッハ2契約はレビュー済み（Reviewed）。gold questions は32問、全部エンコードして通っている。

いまは **Phase 5 ——「このまま続けるか・作り直すか・止めるか」を判断する評価フェーズ**。ここが本当に進行中で、まだ結論は出していない。

判断材料になりそうな早期のシグナルは2つ出た。**これは証明じゃなくて、あくまでシグナル**として書く。

- **再現性**。gold を伏せた状態で、別の分析者（GPT系）に32問をブラインドで答えさせた。実質的な不一致は **0/32**。表記ゆれ（`V7` と `V7/I` みたいな）は出たけど、分析の中身は割れなかった。
- **有用性**。バッハ BWV 846 の露出部を検索させたら、主題の登場を **人手では書いていなかったぶんも含めて機械的に発見した**（テノール・バス・ソプラノに埋もれていた3つ）。手で注釈するより先に、構造のほうから拾えた。

ただ、これは1コーパス・盲検者1人規模の話で、まだ experimental（0.x）。namespace も後方互換も約束していない。「これで正しさが証明された」と言える段階ではない。*言いたい気持ちはあるけど、まだ言わない。*

でも個人的には、この2つが出た時点でわりと手応えを感じている。少なくとも、54日止まっていたときの「何を検証すればいいか分からない」からは抜けた。

## これからと、この先の本

次は Phase 5 の判断そのもの。そして本来の目的地だった **WCC への再統合**。「説明可能な生成」に戻る。生成エンジンが吐いた理由を LOGOS で受けて、ルールで評価して、人間が読める形で見せる。ここまで繋がると、最初に書いた「なぜこの音がここにあるのか」に、機械が根拠つきで答えられるようになる。

射程としては、XAI 音楽（AI の作曲意図を人間が読む）、計算音楽学（バッハの構造を定量比較する）、音楽教育（対位法の禁則を根拠つきで自動添削する）あたりを見ている。

この記事はさわりです。6つの基本要素、DSL の文法、ルール体系、受け入れゲート G1〜G8、そして実際のエンコード例——中身は **入門書のほうでちゃんと書く**。

音は、ただ聞こえるだけじゃなくて、そこにある理由がある。それを書けるフォーマットの話でした。
