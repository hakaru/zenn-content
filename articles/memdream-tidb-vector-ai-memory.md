## 何が問題だったか

普段の開発は Claude Code + Codex + Gemini CLI の3本立て。iOS/macOS アプリを8本並行で作ってる。

AI とのセッションは切れるとコンテキストがリセットされる。CLAUDE.md に書けば多少残るけど、プロジェクトをまたいだ記憶は持てない。M2DX(FM シンセ)で直したオーディオスレッドのバグと同じパターンが TineModeler3 にもあるのに、AI はそれを知らない。

1プロジェクトの記憶なら既存ツールでなんとかなる。横断ができない。そこが作った動機。

## 登場するアプリを先に紹介しておく

この記事の「記憶」の生産者は、自分が並行開発してる iOS/macOS アプリたち。例として何度も出てくる2本だけ、ちゃんと紹介しておく。

### M2DX — MIDI 2.0 対応 DX7 互換 FM シンセサイザー

ヤマハ DX7(1983年の名機)互換の FM 音源を、6オペレータ × 32アルゴリズムで Pure Swift 6 実装した iOS シンセ。App Store で配信中（無料）。

https://apps.apple.com/jp/app/m2dx/id6763840208

中身は3つのリポジトリに分かれてる。アプリ本体の M2DX、FM 合成エンジンの M2DX-Core、MIDI 2.0 プロトコルライブラリの MIDI2Kit。memdream ではこの3つを「m2dx-ecosystem」という1つのエコシステムとして括ってる。この記事で「エコシステム記憶」の実例として出てくるのはこいつら。

シンセなのでオーディオのレンダースレッド(音を生成する処理。1秒間に約48,000サンプルを休まず吐き続ける)があって、ここは「アロケートしない、ブロックしない、ロックを取らない」が鉄則。すぐ後に出てくる FXParamBox のバグは、この鉄則をうっかり破ってたという話。

ライブ演奏・インタビュー・フィールドレコーディングを確実に録るための録音アプリ。iCloud / Dropbox / Google Drive / Backblaze B2 へのクラウド同期に対応してて、App Store で配信中。

https://apps.apple.com/us/app/1take/id6757945099

https://testflight.apple.com/join/Vk9S4kmn

## 記憶は3層 — 生ログ・要約・関係

memdream の記憶は3層になってる。生の体験を全部そのまま覚えておくんじゃなくて、人間の記憶と同じで「整理」が入る。

1層目は観測(observations)。生の作業ログで、今 2,218件ある。

「1Take の paywall バグを直した」「M2DX のオーディオスレッド安全性をレビューした」…セッション中に起きたことをそのまま記録する。

記録するとき、本文を Ollama の bge-large というモデルでエンベディング(= 文章を 1,024個の数値の並びに変換したもの。意味が近い文章ほど近い数値になる)にして、TiDB の `VECTOR(1024)` カラムに一緒に保存する。あとで「意味が近い記憶」を数値の距離で探せるようにするため。これがベクトル検索。

2層目は統合記憶(consolidated memories)。要約された知見で、今 217件。

観測が溜まるとノイズが増えて検索精度が落ちる。だから dream-agent というバッチ処理が 12件ずつまとめてローカル LLM(qwen3:14b)に要約させる。M2DX の観測12件が「M2DX RT-Safety とロックフリーアーキテクチャ修正」という1つの記憶に昇華される、みたいな。

スコープが3段階ある。project(プロジェクト単位)、ecosystem(プロジェクト群単位)、global(全体)。M2DX・M2DX-Core・MIDI2Kit は「m2dx-ecosystem」として括ってあるので、M2DX のセッションで記憶を引くと MIDI2Kit の修正履歴も一緒に返ってくる。

3層目はナレッジグラフ(knowledge graph)。関係を表すデータで、今 1,187本。

```
M2DX --implements--> lock-free triple buffer
M2DX --depends-on--> MIDI2Kit
TineModeler3 --fixed--> SPSC data race
```

主語-述語-目的語の3点セット(トリプル)。ベクトル検索は「意味が近いもの」を引くけど、グラフは「構造的につながってるもの」を引く。役割が違うので両方持つ。

接続は MCP(= Model Context Protocol。AI ツールに外部機能を生やすための共通規格)サーバーとして実装してあって、Claude Code から `memory_observe`(記録)、`memory_search`(検索)、`memory_recall`(統合記憶の取得)など9ツールが呼べる。

## 実際に効いた場面

M2DX のオーディオエンジンで `FXParamBox` というクラスが `os_unfair_lock` を使ってた。音を生成するスレッドは「絶対にロックを取らない」が鉄則なんだけど、見落としてた。レビューで見つけて、ロックなしの実装(Atomic triple buffer)に置き換えて、memdream に記録した。

その後、別プロジェクト TineModeler3 のセッションで `memory_search("lock-free audio thread")` すると、M2DX の修正履歴がヒットする。「Atomic triple buffer で置き換えた」という解決策付きで。

*プロジェクトが違うのに、同じ問題の解決策が引ける。*

1回の修正経験が、他のプロジェクトの未来のセッションに伝播する。これが横断記憶の効果で、ファイルベースの記憶(CLAUDE.md とか)では構造的にできないこと。

## dream-agent — 寝てる間に記憶を整理する

やってることは4つ。

1. 未処理の観測をプロジェクト別に拾う
2. 12件ずつチャンクにして、ローカル LLM に「要約して、関係をトリプルで抽出して」と投げる
3. 返ってきた JSON から統合記憶とナレッジグラフを INSERT
4. 同じエコシステム内のプロジェクトを横断した分析もやる

8週間で7回走らせた。

| 実行 | 処理した観測 | 生成された記憶 | トリプル |
|---|---|---|---|
| 1回目 | 168 | 19 | 111 |
| 2回目(直後) | 0 | 0 | 0 |
| 3回目 | 17 | 7 | 32 |
| 4回目(一括インポート後) | 1,468 | 129 | 695 |
| 5回目 | 324 | 39 | 225 |
| 6回目 | 124 | 18 | 100 |
| 7回目(同日・追い炊き) | 30 | 5 | 24 |

2回目の「全部0」は失敗じゃなくて正常動作。観測テーブルに `consolidated` というフラグ(処理済み印)があって、dream-agent は `WHERE consolidated = FALSE` で未処理分だけ拾う。だから何回走らせても二重処理が起きない。冪等(= 何度実行しても結果が同じ)になってる。仕組みは BOOLEAN カラム1個。

面白かったのはエコシステム横断分析。M2DX と M2DX-Core と MIDI2Kit で別々に直した並行処理とバッファの問題を、LLM が勝手に「Concurrency Management and Buffer Optimization」というエコシステム全体の傾向としてまとめてきた。

*3つのプロジェクトを個別に見てたら気づかないパターンが、束で見ると浮かび上がる。*

## なぜ TiDB か — 決め手はベクトル検索「以外」

ベクトル検索だけなら選択肢は山ほどある。Pinecone、Qdrant、pgvector…。DB 比較は過去記事でやったので、ここでは memdream を実装して「RDB の機能がそのまま使えて助かった」場所を3つ。

重複排除は `INSERT IGNORE` 1文で済む。同じ内容を2回記録しない仕組みが要る。memdream では `content_hash` という生成カラム(= 他のカラムから DB が自動計算するカラム。project_id + title + content の SHA2 ハッシュ)に UNIQUE 制約をかけてる。アプリ側は `INSERT IGNORE` で投げるだけ。ベクトル専用 DB だと「先に類似検索して、閾値以上なら書かない」をアプリで書くことになる。

エコシステム展開は JOIN。「M2DX の記憶をくれ」と言われたら projects テーブルの `ecosystem` カラムを見て、兄弟プロジェクトに展開して、まとめて返す。外部キーと JOIN の世界。グラフも記憶も観測も同じ DB にあるから、1往復で済む。

冪等性はフラグ1個。さっきの `consolidated` フラグに対して `UPDATE ... SET consolidated = TRUE` するだけで増分処理が成立する。

*これ全部、ベクトル専用 DB だとアプリ側に持つロジック。* TiDB だと SQL で書くだけ。

## HTAP は「使ってみると」こうなる

TiDB の看板機能が HTAP(= 取引処理と分析処理を1つの DB で捌く設計)。書き込みは行ストア(TiKV)が受けて、ベクトル検索や集計は列ストア(TiFlash)のレプリカで処理される。エンジンが物理的に分かれてる。

memdream の負荷パターンはこれにきれいにハマった。昼はセッション中の `memory_observe` がポツポツ INSERT して、夜は dream-agent が大量読み出しと集計をかける。昼の書き込みと夜のバッチが同じストレージを取り合わない。

正確に言うと完全な無干渉ではない。TiFlash は書き込みを非同期で追いかけて取り込み続けるし、ベクトルインデックスの構築が追いつくまでは新着データの検索が遅くなることもある(公式ドキュメントにも明記がある)。それでも「分離されてる」恩恵は実測済みで、毎分30件 INSERT を流し続けても集計クエリの応答が 14ms で安定する、というのが過去記事の結果。

## TiDB で嵌まったところ

### LIMIT にパラメータが渡せない

```typescript
// ❌ これが TiDB で落ちる
ORDER BY distance ASC LIMIT ?
// → Error 1210: Incorrect arguments to LIMIT
```

prepared statement(= SQL の雛形に値を後から流し込む実行方式)で LIMIT に値を渡すと落ちる。掘ってみると、TiDB は LIMIT の値が「整数型」で届かないと弾く仕様で、Node.js の mysql2 は JS の number を DOUBLE(浮動小数点)として送る。この組み合わせで確実に死ぬ。MySQL 本家は文字列でも強引に変換してくれるけど、TiDB は厳格。

対処はバリデーション済みの整数を直接埋め込む。

```typescript
// ✅ limit は Zod で 1〜50 の整数と検証済み
ORDER BY distance ASC LIMIT ${limit}
```

*同じ轍を2回踏んだ。* `memory_search` で直したのに、`memory_timeline` に同じコードが残ってて1週間後にまた踏んだ。

### ベクトルインデックスは次元固定が必須

`VECTOR` じゃなくて `VECTOR(1024)` と次元を固定しないとインデックスが張れない。インデックスのアルゴリズムは HNSW(= 近似的にご近所を探す索引。厳密解を捨てて速度を取る)のみで、距離関数はコサインと L2 だけ。あとベクトル検索自体まだベータ扱い。

HNSW と WHERE 句の組み合わせ制限は過去記事で踏んだやつなので省略。

### パスワードを回したらメモリが全滅した

これは TiDB の SQL じゃなくて Cloud 運用の嵌まり。TiDB Cloud のパスワードをローテーションした直後から、`memory_observe` が全部こけ始めた。

```
Error 1045: Access denied for user '****.root'@'...' (using password: YES)
```

DB が落ちたのかと思った。でも新しいパスワードで直に繋ぐと普通に通るし、観測も読める。*じゃあ何が拒否されてるんだ。*

犯人は memdream の MCP サーバー自身。これは起動しっぱなしの常駐プロセスで、立ち上がるときに mysql2 の `createPool` で接続プールを張る。このプールが**古いパスワードを握ったまま**で、クラウド側で旧パスワードが無効化された後も、起動済みのプロセスはずっと旧パスワードで叩き続けてた。ローテーション前に開いてた Claude セッションが何本かいて、そいつらが全滅。当日の朝に立ち上げ直したセッションだけが新パスワードで生きてた、という分かれ方だった。

直し方は MCP サーバーの再接続(プロセスを再起動して新しい env を読み直す)。それだけ。

*managed DB のパスワードを回すなら、繋ぎっぱなしのプールも一緒に張り直す。* アプリのバグじゃなくて「長命プロセス × 認証情報の差し替え」の噛み合わせ。自分でいつでもローテーションできるクラウド DB だからこそ踏む穴で、しかもエラーメッセージは「認証失敗」としか言わないので、DB 障害だと誤読しやすい。

## 運用して出てきたゴミ

正直コーナー。projects テーブルには一時 25 プロジェクトいて、うち何件かは大文字小文字違いの重複(PeerClock と peerclock、M2DX と m2dx)。slug の正規化を入れる前のセッションが作ったゴミ。エコシステム未設定(NULL)のプロジェクトも18件あった。

スキーマの UNIQUE 制約でも防げなかった。「書き込む側の規律」はスキーマだけでは守れない、という運用の学び。

(追記)この記事を書いてる途中で slug 正規化(小文字化 + パスは basename 抽出)を `ensureProject` に入れて、既存のゴミは移行スクリプトで統合した。25 → 17 プロジェクト、重複ゼロ。直したそばから別セッションの旧ビルドが重複を1個作ってくれて、「src を直してもビルドするまで MCP サーバーには反映されない」というオマケの学びも付いた。

(追記2・公開時点)その後の新規開発で 23 プロジェクトまで増えた。17 → 23 はゴミの再発じゃなくて、新しく触ったリポジトリがそれぞれ記憶を持ち始めただけ。正規化を入れて以降、大文字小文字違いの重複はゼロのまま。スキーマの制約じゃなく `ensureProject` という1つの入口に規律を寄せたのが効いてる。*「書き込む側の規律」は、書き込む経路を1本に絞ると守れる。*

あと Ollama 由来の制約として、bge-large の入力は実質512トークンなので、観測の content は500文字以内に切ってる。長文を全部覚えるんじゃなくて「要点を短く書いて記録する」運用がむしろ検索精度に効く。

## mem9 じゃだめなの？

白状すると、memdream を作り始めた4月下旬、mem9 の存在を知らなかった。PingCAP 自身が出してる managed なエージェントメモリ製品(TiDB Cloud ベース)で、リリースは2026年3月。出たばかりだった。知ったのは、この記事を書くためにコンテストページを読んだとき。

で、調べてみたら設計が面白いくらい似てる。mem9 の記憶は「セッショントレース(生ログ)・抽出インサイト(LLM が自動抽出した事実)・ピン留め(手動の永続記憶)」の3種類。memdream の3層(観測・統合記憶・ナレッジグラフ)と発想がほぼ同じ。エージェントの記憶を真面目に考えると、だいたいこの形に収束するんだと思う。

mem9 は Apache-2.0 でサーバーまで全部公開されてるので、ドキュメントとソースを読み込んで比較した。

| 観点 | memdream | mem9 |
|---|---|---|
| 記録 | MCP ツール + CLAUDE.md ルール(規律依存) | フックで全自動 |
| 統合 | dream-agent の手動バッチ | 自動・非同期(重複統合 + 世代管理つき) |
| 検索 | ベクトルのみ | キーワード + ベクトルのハイブリッド |
| スコープ | project / ecosystem / global | space + appId(プロジェクト単位なし) |
| ナレッジグラフ | RDF トリプル 1,000本超 | なし(仕様書が明示的に対象外と記載) |
| 埋め込み | Ollama ローカル | 必ずサーバー側 |
| 共有 | なし(個人用) | API キー共有でマシン・ユーザー跨ぎ |
| セットアップ | TiDB + Ollama + MCP 登録 | プラグイン2コマンド |

mem9 が勝ってる部分は素直に認める。フックによる全自動記録は「書き込む側の規律」問題(さっきの slug 事件みたいなやつ)を設計で潰してるし、抽出インサイトは dream-agent がバッチでやってる統合をリアルタイムでやって、古くなった記憶に世代管理(`superseded_by`)まで付ける。ハイブリッド検索も今動く。チームで記憶を共有したいなら、議論の余地なく mem9 が正解。

それでも個人の横断開発で memdream を使い続ける理由は4つ。

- プロジェクト/エコシステム単位のスコープが mem9 にはない。space の中はフラットで、「M2DX のセッションに依存ライブラリ MIDI2Kit の記憶を自動で混ぜる」ができない。これは memdream の存在理由そのもの
- ナレッジグラフがない。「何が何に依存してるか」を構造で辿る記憶は守備範囲外
- hosted の mem9 は埋め込みも LLM 抽出も必ずサーバー側で、コードの作業ログが外部に出る。セルフホストすれば回避できるけど、それなら運用の手間は自作と大差ない
- MCP サーバーがない(対応はランタイムごとの専用プラグイン + REST。MCP は将来の提案段階)。MCP 対応クライアントなら何でも繋がる、とはいかない

逆に言うと、この4つが要らないなら自作する理由はあんまりない。知ってたら作らなかったかというと…スコープとグラフが欲しかったので、たぶん作ってた。

### さらに新しいもの — Agent State Stack と Auto Embedding

書いてる最中の2026年6月11日、PingCAP が **Agent State Stack**(TiDB Cloud Zero + mem9 + drive9)を発表した。エージェントの「記憶・状態・成果物」をマネージドで一式持つスタックで、memdream がやってることのマネージド版がまた一段ぶん増えた格好。

方向性は完全に被ってる。それでも自作を続ける理由は前述の4つ(スコープ・グラフ・ローカル埋め込み・MCP)そのまま。とくに **Auto Embedding(サーバー側でテキスト→ベクトル変換してくれる機能)** を使わず Ollama bge-large のローカル埋め込みに固執してるのは、*コードの作業ログを外部に出したくない*から。マネージドが楽なのは分かってて、それでも「記憶の素材＝自分のコード」だけはローカルに置く、という線引き。

つまり memdream は「マネージドの Agent State Stack を、スコープ付き + 知識グラフ + ローカル埋め込みで自前実装した版」。大半の人はマネージドが正解だと思う。でもこの3点が要るなら、自作の意味はまだある。

## まとめ

8週間運用しての TiDB 評価。

効いたのは、生成カラム + UNIQUE での重複排除、エコシステム JOIN、フラグでの冪等性。ベクトル検索と RDB 機能が同じ場所にあることで、記憶システムの実装量はかなり減った。

ハマったのは、LIMIT のパラメータ問題(mysql2 との組み合わせ)、ベクトル次元の固定、ベータ由来の制約。

コストは無料枠の誤差レベル。個人の開発記憶用途で課金が発生する未来が見えない。

これから:

- dream-agent を launchd で毎晩自動実行(本物の「睡眠中の記憶整理」にする)
- TTL(= 行に有効期限を付けて自動削除する機能)で古い観測を自動アーカイブ。Starter だと削除ジョブは15分間隔固定
- 全文検索(ベータ。今はフランクフルトとシンガポールのみ)が東京リージョンに来たら、ベクトル + キーワードのハイブリッド検索
- Codex / Gemini CLI からの MCP 接続

記憶が溜まるほど、セッション開始時の「このプロジェクトはですね…」という説明し直しが消えていく。8週間でだいぶ消えた。次の8週間でどこまで消えるか。
