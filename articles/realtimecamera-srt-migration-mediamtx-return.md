## 「iPhoneとサーバの間、SRTにしたい」

[前回](/hakaru/articles/realtimecamera-livekit-recording-server)、iPhone のカメラ映像を LiveKit（セルフホスト SFU）でサーバに送って録画する基盤を作った。あのとき方式選定で **MediaMTX + SRT を蹴って LiveKit を選んだ**。決め手は制御チャネル。カメラの遠隔操作が要件にあって、LiveKit なら RPC が標準で乗っているから、という理由だった。

それから2ヶ月弱。iOS アプリも遠隔操作もダッシュボードも一通り動くようになった段階で、冒頭の一言が来た。

*せっかく作った RPC の配線、どうすんの…* と思いつつ要件を整理したら、最終的に **LiveKit 完全撤去 + MediaMTX 出戻り**という結論になった。この記事はその設計編。実装はまだ1行も書いてない。書いてないのに、設計レビューだけでかなり転んだので先にそれを書く。

## LiveKit は「映像伝送」だけじゃなかった

「iPhone→サーバを SRT に変える」と言ったとき、変わるのは映像の経路だけに見える。実際は違う。現行システムで LiveKit が担っている機能は5つある。

- 映像の publish（iPhone → SFU）
- ライブ視聴（ブラウザが subscribe）
- 遠隔制御（RPC で `camera.start` とか投げる）
- 状態報告（participant attributes で発熱・バッテリを配信）
- 録画（Track Egress で無変換 MP4）

SRT は1番目しか置き換えない。残り4つの行き先を決めないと設計にならない。

## 動機を4択で聞いたら全部YESだった

なぜ SRT にしたいのか。選択肢を出して確認した。

- 回線が不安定な環境での安定伝送（SRT の再送制御・遅延バッファ）✅
- OBS / vMix みたいな配信業界標準ツールとの連携 ✅
- WebRTC/LiveKit の複雑さの排除 ✅
- WebRTC の輻輳制御に画質を下げられたくない、高ビットレート固定 ✅

全部だった。3つ目に「複雑さの排除」が入った時点で、「LiveKit を残して SRT Ingress だけ足す」という折衷案は消える。LiveKit + Ingress + Redis になって、構成はむしろ増えるので。

## 効いたのは「遠隔制御どうする？」の一問

ライブ視聴は「低遅延必須（〜1秒）」、録画は「現行相当を維持」。ここまでは想定内。転換点は遠隔制御の扱いだった。

回答: **廃止**。

前回 MediaMTX を蹴った理由、そのものが要件から消えた。制御チャネルが要らないなら、SRT 受信・WebRTC(WHEP) 再生・録画を1プロセスでやってくれる MediaMTX が最短になる。livekit-server + egress + redis の3コンテナが mediamtx 1コンテナになり、RPC・attributes・トークン grant の配線も全部消える。

前提がひとつ変わると最適解がひっくり返る。2ヶ月前の自分の選定が間違っていたわけじゃないのが救い。*あのときは制御チャネルが要件だったんだって…*

## iOS 側: Larix は死んでいた

サーバ側が MediaMTX なら、iPhone から SRT を送る側をどうするか。「Larix のライブラリ使える？」と聞かれて調べたら、**Larix Broadcaster SDK は sunset（提供終了）で購入不可**になっていた。公式サイトに "not available for purchase" と明記されている。アプリとしての Larix Broadcaster は健在だけど、自作アプリに組み込む道は閉じている。

残る選択肢は2つ。

| | HaishinKit (SRTHaishinKit) | 独自実装 (libsrt + VideoToolbox + TS mux) |
|---|---|---|
| 実装範囲 | エンコード〜SRT送出まで全部入り | MPEG-TS mux を自分で書く |
| ライセンス/保守 | BSD-3、10年開発でメンテ活発 | libsrt 更新に永久に自分で追従 |
| Swift 6 | strict concurrency 対応済み | C API との橋渡しを自前設計 |
| 制御の自由度 | フレームワークの抽象の内側まで | SRT 統計を直接読んで適応ビットレートも可 |
| 工数感覚 | 1 | 4〜6 |

MPEG-TS の mux（PCR/PTS/DTS のタイミング設計）はバグの温床で、片手間で書ける規模じゃない。なので **HaishinKit を採用して、`StreamingEngine` というプロトコル境界の裏に置く**ことにした。将来「SRT 統計を読んで適応ビットレート制御を極めたい」となったら、境界の裏だけを libsrt 直接実装に差し替える。完全制御の代金は、必要になってから払う。

## 新アーキテクチャ

```
iPhone (HaishinKit, SRT publish)
   │ SRT (UDP, AES暗号化)
   ▼
MediaMTX ── WHEP/WebRTC ──▶ ブラウザ（〜1秒でライブ視聴）
   │ ├ 録画 (fMP4セグメント→そのままMP4として再生可)
   │ └ hooks ──▶ control-server（認証・録画ポリシー・SQLiteインデックス）
```

control-server（Node/TS）の「メディアを中継しない」原則は前回から変わらず。LiveKit webhook の代わりに MediaMTX の hooks を受けて、録画の自動/手動ポリシーと一覧・Range 配信・保持期限削除を今まで通りやる。

## 設計書を AI エージェント21体にレビューさせたら17件刺さった

spec を書いた後、コミット前にマルチエージェントのレビューを回した。構成は3レンズ。

- **repo整合**: spec が既存コードについて言ってること、実在するか
- **内部整合**: spec 単体で矛盾・曖昧・プレースホルダがないか
- **技術事実**: MediaMTX / SRT / HaishinKit の仕様主張を Web で裏取り

3レンズが出した指摘18件を、それぞれ別のエージェントが「反証しろ」というプロンプトで潰しにいく。生き残ったのが17件、棄却1件。合計21体。

*17/18が本物って、自分の設計書どんだけ穴あったの…* と思いながら見たら、実際どれも痛かった。抜粋する。

### 実装したら publish 全拒否になるやつ

MediaMTX の外部認証 hook（`authHTTPAddress`）は、SRT パスフレーズとは**独立に publish にも適用される**。spec は「publish はパスフレーズで完結するから hook は視聴側だけ検証」と書いていた。このまま実装すると、パスフレーズが合っていても全 publish が認証拒否される。`authHTTPExclude` に publish を明示追加する必要があった。

### hook 名が2週間前の知識で死んでるやつ

`runOnReady` / `runOnNotReady` は MediaMTX v1.19.3 で `runOnAvailable` / `runOnUnavailable` にリネームされていた。旧名は deprecated 警告付きで動く。動くのが一番たちが悪い。バージョン固定を spec に明記して新名に統一。

### 論理的に観測不能になるやつ

現行は「online（接続中）だが未配信」という状態がある。iPhone が LiveKit room に常時接続して RPC を待つから。SRT は配信するときだけ接続するプロトコルなので、移行後この状態は**サーバから原理的に観測できない**。「現行 UI のまま、情報源だけ変更」と書いていた spec は成立しない。online と配信中をバッジごと統合する設計判断に書き換えた。

### 手元で再現実験までしてきたやつ

E2E テストは ffmpeg で SRT を publish する計画だった。レビューエージェントが実際にこの開発機で `ffmpeg -f mpegts srt://...` を叩いて **Protocol not found を実証**してきた。Homebrew core の ffmpeg は `--enable-libsrt` なしでビルドされている。libsrt 入りビルドの入手手段まで含めて spec に前提条件を追記。

エージェントに「根拠には実ファイルパスか URL 必須、でっち上げるな」と縛りを入れて、さらに反証専用エージェントを重ねる構成は、レビュー精度に露骨に効く。棄却された1件も「spec 本文と食い違う主張」という妥当な理由で落ちていた。

## で、Codex がそのレビューをレビューして blocker を3件出した

ここまでやった上で「codex レビューさせて」と追加注文が来たので、GPT-5.5 (Codex) にも spec を投げた。結果は **Request changes**。blocker 3件、Important 8件、Minor 3件。21体レビューを通過した spec に対して、まだこれだけ出る。

一番面白かったのが `authHTTPExclude` の裁定。21体レビューの反証エージェントは「除外された action は内部認証にフォールバックする」と結論して、spec には「`authInternalUsers` で publish を許可しておく」と書いた。Codex は公式ソースを追って「**フォールバックではなく即時許可（認証のバイパス）**」と反論。v1.19.3 の `manager.go` を自分で確認したら、除外にマッチした瞬間 `return "", nil` で認証成功だった。Codex の勝ち。しかもこの除外は protocol を区別しないので、SRT のつもりで publish を除外すると **WHIP（WebRTC の publish）までパスフレーズなしで通る**。未使用サーバの無効化と WHIP 非公開まで含めて封鎖する設計に書き直した。

他の blocker も痛い。「HKDF の材料にする device key、DB には SHA-256 ハッシュしか保存してないから起動時に再導出できないよ」（現行コードの registry.ts を読まれている）、「既存 SQLite の `egress_id NOT NULL UNIQUE` と新スキーマが衝突する。マイグレーション未定義」。あと「MediaMTX の `recordDeleteAfter` は**既定 1d** なので、明示的に無効化しないと録画が1日で勝手に消える」という時限爆弾も。

AI のレビューを AI が反証して、その結論をさらに別の AI がひっくり返して、最後は人間（と公式ソース）が裁定する。*どこまで再帰すんの…* とは思うけど、レイヤーを重ねるたびに実際に本物の欠陥が出てくるので止める理由がない。

## 計画1（スパイク）を subagent 駆動で回した

設計が固まったので実装に入る。ただし本実装（server / iOS / dashboard / deploy）の前に**スパイク**を1本置いた。HaishinKit → MediaMTX → WHEP が実際に繋がるかを実機で確かめる土台を作る、それだけの計画。ここで転ぶなら設計に戻る。

進め方は subagent 駆動。タスクごとに新しい実装エージェントを立て、終わったら別のレビューエージェントが仕様準拠と品質の2軸で判定し、指摘が出たら実装エージェントに戻して修正させ、修正差分だけをスコープを絞って再レビューする。私（オーケストレーター側）は自分で手を動かさない。5タスクで12コミット。

面白かったのは、**どの層のレビューも必ず何か出した**こと。1発で通ったタスクはゼロ。

### 既定で有効な publish 経路が1本残っていた

Task 1（MediaMTX 環境構築）のレビュー。spec §4.2 は「publish 経路を SRT だけに限定する」ために RTSP/RTMP/HLS を無効化しろと書いていて、実装もそのとおりになっていた。レビューエージェントが公式の設定ファイルを引いてきて言った——**MediaMTX 1.19.3 は MoQ (Media over QUIC) サーバが `moq: true` で既定有効**、しかも publish を受け付ける。

`authHTTPExclude` の除外は protocol を区別しない（Codex が見つけたやつ）ので、SRT のつもりで publish を除外すると MoQ 経由でも無認証で publish が通る。spec の列挙漏れがそのまま実装に降りていた。ポートが未公開だったので実害はなかったけど、本番構成に持ち込んだら普通に穴。

### 公式ドキュメントのサンプルが間違っていた

Task 3（iOS）。HaishinKit で SRT を送るコードを書かせたら、実装エージェントがこう言ってきた。

> `MediaMixer#startRunning()` の呼び出しが、ブリーフにも公式 doc のスニペットにも欠落している

ソースを追ったらそのとおりだった。`addOutput()` は配列に append するだけで、フレームを実際に配送する Task は `startRunning()` の中でしか作られない。**呼ばないと SRT 接続は成功する。エラーも出ない。映像だけが 1 バイトも流れない。**

*一番タチが悪いやつじゃん…*

公式ドキュメントの Publish サンプルをコピーして「繋がってるのに映らない」で数時間溶かす未来が、ここで消えた。スパイクを先に置いた元が取れた瞬間。

### エンコード設定、既定値だと全部ダメ

同じく Task 3。`VideoCodecSettings` は何も指定しないとこうなる。

| 項目 | 既定値 | 要件 |
|---|---|---|
| `videoSize` | 854×480 | 1920×1080 |
| `profileLevel` | Baseline_3_1 | 1080p に足りない |
| `maxKeyFrameIntervalDuration` | **2秒** | ≤1秒（WHEP 起動 1秒以内のため） |
| `scalingMode` | `.trim`（aspect-fill + crop） | — |
| `MediaMixer.videoOrientation` | `.portrait` | 横 |

最後の2つの組み合わせが厄介で、最終レビューが拾ってきた。縦キャプチャ（1080×1920）を横セッション（1920×1080）に `.trim` で入れると**約1.78倍の中央クロップ**になる。そして僕が書いた検証手順は「ffprobe で `1920,1080` を確認」だった。ffprobe が読むのはセッション寸法なので、**正しい画角でもクロップでも同じ値が出る**。検査をすり抜ける。

このまま実機測定をやると、1.78倍に拡大された絵に 6Mbps を割り当てて「画質どうですか」を判定することになっていた。測定そのものが無意味になるところだった。

### 修正が新しいバグを産んだ

Task 3 のレビューで、SpikeView の actor に競合が2件見つかった。`start()` の中で `await` を4回またぐ間、インスタンスへの参照がまだ代入されていない。だから「配信開始をタップしてすぐ画面を戻る」と `stop()` が空振りして、カメラと SRT ソケットを掴んだまま誰も止められなくなる。二重タップも1回目のインスタンスが孤立する。

実装エージェントが `idle/starting/running/stopping` の状態機械を入れて直した。両方 ADDRESSED。**ただし修正差分に新しい穴が入っていた。**

中断されて自己破棄した経路が例外を投げずに正常 return するので、View 側が「成功した」と解釈して `status = "配信中"` を書く。actor はカメラもソケットも解放して idle なのに、UI は配信中で固まる。*さっき直した症状と全く同じやつ…*

スコープを絞った再レビュー（fix 差分だけを見る）がこれを捕まえた。修正を無条件で信用せず、毎ラウンド差分を見に行く構成にしておいてよかった。round 2 で `.cancelled` を投げる形にして決着。

### 測定項目そのものが1軸抜けていた

Task 4 は実機測定のチェックリスト。ここのレビューは spec との突き合わせで **jitter の注入が丸ごと無い**と指摘してきた。spec §10 は「帯域制限・packet loss・jitter」の3軸を要求しているのに、loss と帯域しか書いていない。

SRT を選んだ一番の理由が「不安定回線での安定伝送」なのに、その検証軸が1本欠けたまま GO 判定に到達するところだった。**計画書を自分で書いて自分で実装すると、こういう欠落は絶対に自分では見つからない。**

## 数えてみた

計画1 だけで、実装エージェント・レビューエージェント・修正ラウンド・最終レビューを合わせて20体近く回している。設計フェーズの21体と合わせると40体超。

出てきた指摘のうち「実装したら動かない／測定が無意味になる」級:

- spec レビュー（21体）: 認証で publish 全拒否、hook 名リネーム、観測不能な状態
- Codex レビュー: `authHTTPExclude` はバイパス、KDF の材料が DB に無い、録画が既定 1日で消える
- 実装レビュー: MoQ 経由の publish、公式 doc の `startRunning()` 欠落、1.78倍クロップ、jitter 軸の欠落

*これ全部、素直に実装してたら実機の前で全部踏んでるな…*

## まとめ

- 要件（遠隔制御）が1個消えたら、2ヶ月前に蹴った MediaMTX が最適解に戻ってきた
- Larix SDK は sunset。iOS の SRT 送出は HaishinKit 2.2.5 + 差し替え境界で
- 設計書は書き上げてからが本番。21体レビューで17件、続く Codex レビューで blocker 3件
- 実装フェーズもレビューが毎回何か出した。1発で通ったタスクはゼロ
- **修正自体がバグる**。スコープを絞った再レビューを毎ラウンド挟むと捕まる
- 公式ドキュメントのサンプルコードは疑ってよい。ソースが正

残りは実機測定。glass-to-glass 遅延・loss/帯域/jitter の劣化試験・回線断からの復帰を測って、通れば計画2（server）へ。ここで転んだら画質プリセットか適応ビットレートの設計に戻る。測ったらまた書く。
