## 結論

**Zelquo** っていう、iPhone/iPad でライブ演奏するための AUv3 ホストアプリを計画してる。`Setlist → Song → Scene → Layer` という構造で、1つの Layer に複数の AUv3 音源を重ねられるのが売りの1つ。

このアプリ、まだ**1行も本体のコードを書いてない**。代わりにこの5日間、ずっとこれだけを検証してる。

> **同じ AUv3(たとえば KORG Module)を、iPhone/iPad 上で2インスタンス同時に鳴らせるか**

理由は単純で、これが No だったら Layer 機能の前提が崩れて、アーキテクチャから考え直しになる。だから作り始める前に、この1点だけを実機で白黒つけたかった。

で、今のところ何が起きてるかというと、**この Yes/No を確実に判定するための検証ハーネスだけで、285件のテストが動いてる**。肝心の実機判定はまだ1回も走ってない。

## なぜこの1点がそんなに怖いか

Zelquo の Layer は「同じキーレンジに複数の音源を重ねる」機能で、ユーザーが同じ AUv3(同じ KORG Module を別パッチで2つ、とか)を重ねるのは普通に起きる操作として想定してる。

ところが AUv3 のホスティングって、Apple のドキュメントを読んでも**サードパーティ製 AU を同一プロセス内で複数インスタンス同時実行できるかがはっきり書いてない**。Simulator では AU 自体まともに動かないし、フェイクで代替できる部分でもない。実機で、実際の KORG Module を使って、実際に確かめるしかない。

*ここでコケたら Layer は「1音源1レイヤーまで」に仕様を落とすか、まるごと設計をやり直すことになる*。V1 の中核機能が崩れるレベルの依存関係。

## 最初の計画では、この検証は Task 17 だった

最初に書いた実装計画では、全18 Task のうち、この multi-instance 検証は **Task 17**(実機 acceptance runner)に置いてあった。Task 1〜16 で永続化・runtime state machine・MIDI・audio graph・scene 遷移…と一通りの本体アーキテクチャを組んでから、最後にまとめて実機で確かめる順番。

計画レビューでこれが引っかかった。2026-08-08 の教訓としてこう書き残した。

> 同一AUv3の2-instance起動可否が採用アーキテクチャ全体を無効化し得るのに、完全な実機acceptance Taskまで検証を先送りした。網羅的な最終acceptanceは、早期のfeasibility gateの代わりにはならない。

*言われてみれば当たり前なんだけど、計画を書いてる時は「全部組んでから通しで確認しよう」という発想に自然と流れる*。ルール化したのはこう。

- 技術スパイクを分解する前に、失敗すると後続実装が無駄になる前提を列挙する
- 依存する最初の Task より前に、最小の実機 probe を置く
- Simulator やフェイクで代替できない制約(サードパーティ AU、ハードウェア、OS extension)は、本体アーキテクチャを作る前に実機で検証する

というわけで multi-instance 検証は **Task 2**(スキャフォールドの直後)まで前倒しになった。

## 最初の実装は突き返された

Task 2 は最初、普通に1回で通しの実装を書こうとした。結果、独立レビューで **Critical 4件・Important 8件**の指摘を食らって差し戻し。

- Pass/terminal の判定ロジックが浅い(表面的な成功しか見てない)
- デバイスドライバが診断用のダミーのまま
- `xcodebuild` のステータス取得にバグ

コミットせずに破棄して、**8つの直列サブ境界**に分割し直した。fixture の土台(2a)→ 検証ロジック(2b, 2c)→ デバイス側の前処理(2d)→ 実際のドライバ(2e)→ publisher(2f)→ ラッパー(2g)→ 未署名統合ゲート(2h)、という順で、1つずつ独立レビューを通してからでないと次に進まない運用にした。

これが効いた。以降の各サブ境界は、実装 → 独立レビュー(だいたい Critical/Important が1〜2件出て remediation) → 再レビュー → GREEN、を繰り返してる。たとえば直近の Task 2g0 はこう。

```
Implementer verification: portable 110/110, publisher 44/44,
full portable 210/210, device 285/285(既知の2件を除く)
Reviewer-fresh: helper 5/5, affected 110/110, publisher 44/44,
凍結hash一致、lint/diff/staged監査すべて正常
最終判定: C/I/M=0, Ready YES
```

C(Critical)/I(Important)/M(Minor) が全部ゼロになって初めて次のサブ境界に進む。5日間でここまで来て、まだ 2g の途中。

## ゲート自体の設計もかなり重い

肝心の実機テストを実行する部分(ゲート)は、こういう設計にした。

- iPhone/KORG、iPhone/Effect、iPad/KORG、iPad/Effect の**4役割を固定順で実行**
- 終了コードで結果を返す: Pass=0、KORG No-Go=20、判定不能=21、Effect再試行=22。**XCTest 自体の成功/失敗はゲートの判定に使わない**
- 実機デバイスIDは**ハッシュ化してから記録**、生のIDはJSON・添付ファイル・ログのどこにも残さない
- 4役割すべて Pass した時だけ `multi-instance-gate-lock.json` を生成。これが HEAD と byte-exact で一致し、index/worktree ともにクリーンでないと、以降のダウンストリーム作業はラッパー(`with-auv3-feasibility-gate.sh`)経由で**実行前に弾かれる**

要は「実機で1回動いた」を人間の記憶や口頭確認に頼らず、改ざん不可能な形でリポジトリに固定する仕組み。ここまでやる理由は、この Yes/No 判定を後から疑わなくて済むようにするため。一度 Pass を取ったら、それ以降の実装作業は全部このロックの上に積み上がる。

## まだ答えは出てない

ここまで書いてきて、一番書きたいのはここ。**5日間、285件のテストを積んで、まだ「同じ AUv3 を2つ同時に動かせるか」の答えを一度も実機で見てない**。

理由は単純で、答えを1回で正しく取るための検証ハーネス自体を、間違いなく作ることの方に時間がかかってる。ハーネスが甘いと「動いた気がする」止まりの判定しか出ない。それは今回みたいなアーキテクチャを賭ける判断には使えない。

*正直、じれったい*。でも Task 17 まで検証を先送りしてたら、この段階でこの重さの答え合わせをすることすらできてなかった。

次の記事が書けるとしたら、たぶん「実機で回したら No-Go だった」か「Pass してロックが生成された」かのどちらか。どっちに転ぶかは、まだ自分にも分からない。
