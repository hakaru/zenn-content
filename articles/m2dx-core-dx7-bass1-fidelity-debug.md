DX7の音をSwiftで作り直して、TestFlightで配ってる。あるとき、テスターのひとりからこう言われた。

> 取り込んだ BASS1、Dexed と音が違う。なんか歪んで聞こえる。

*うわ、いちばん効くやつだ。* 自分で「DX7の音を再現した」と言って出してるシンセが「実機(というかDexed)と違う」と言われると、作ってる側はわりと真っ青になる。

で、原因を追いかけたら **結論が5回ひっくり返った**。しかも最後は「エンジンを1個まるごと作り足す」ところまで行った。順番に書く。

## 結論

何だったかを先に書く。

- M2DXのFM音源コア(**Modern**エンジン)は、参照実装(Googleの **MSFA**、そのC移植 **dx7ref**、つまりDexedの「Modern」モード)と **2秒の全区間でサンプル単位ビット一致**してた。エンジンは何も間違ってない。
- 「似てない」の正体は、ユーザーが比較してたのが **Dexedの別エンジン「Mark I」** だったこと。Mark IはOPSチップ(実機DX7の音源LSI)を模した、Modernより暗くて暖かいモード。さらにtranspose未適用のオクターブズレと、DexedのCUTOFF/EQの色付けも乗ってた。同じ「Modern」同士なら一致する。
- 解決は、M2DX-Coreに **Mark I(OPS)エンジンを自前で実装**して、実機の暖かい音も出せるようにした。その暖かさの量を調整するのが **Mark I Depth**(後述)。
- おまけに「BASS1が明るすぎる」と感じる原因の一部は **OP5モジュレータの"居残り"**。これはパッチ(音色データ)通りでバグじゃない。

ここに辿り着くまで5回誤診してる。*なぜ5回も間違えたか* と、*最後どう解決したか* を順番に書く。

## 最初に疑ったもの

「取り込んだ音が歪む/違う」と言われて、まず疑うのはこの辺。

- 出力でクリップ(音割れ)してる
- エイリアシング(= 高すぎる周波数が折り返して乗るノイズ)が出てる
- アプリのFX(Drive / EQ / Maximizer)が悪さしてる
- そもそもFM演算がDexedとズレてる

上から順に潰していった。…つもりが、潰すたびに別の容疑が立つ展開になる。

## 1回目：クリップもエイリアスもFXもシロ

実測した。

仮説 ❌ **クリップしてる**
いちばん"hot"な設定(モジュレータ OL99 / velocity sensitivity 7 / sustainしっぱなし)でも、vel127のピークは **0.1135**(-18.9dBFS)。factoryの FAT BASS が 0.0955 だから、ほぼ同じレンジ。フルスケール ±1.0 まで **9倍** の余裕がある。割れようがない。

仮説 ❌ **エイリアスが乗ってる**
vel127でスペクトルの最高成分が **1.7kHz** 止まり。Nyquist(= 折り返しの境界、48kHzなら24kHz)の遥か下。非整数次の成分は 0.0056%。オーバーサンプリングを on/off しても動かない。折り返しじゃない。

仮説 ❌ **アプリのFX**
既定値を確認。Maximizerは入力ゲイン0でバイパス、Drive0、masterも控えめ。何もしてない。

仮説 ✅ **ただの正当なFM倍音**
centroid(スペクトル重心 = 音の明るさの指標)が vel30→127 で 92Hz→925Hz、約10倍に上がる。これはFM音源として正しい挙動。factoryプリセットはこの変化を 1.01倍にフラットに抑え込んでるから、取り込んだ生のパッチだけが相対的に明るく(harshに)聞こえる。

> 結論(1回目): エンジンは正しい。明るいのは BASS1 という音色の仕様。

…で終わればよかった。でもこの時点で「Dexedの実際の音」とは比べてない。ピークとかcentroidの数字だけ見て「正当な明度」と判断してた。ここが甘い。

## 2回目：Maximizerが犯人(に見えた)

別ルートで、アプリ側のFXチェーンに容疑が向いた。Maximizer(音圧を稼ぐ最終段のリミッタ)の既定状態と天井の設定。取り込んだSysExはFX情報を持たないから、適用されるFXのデフォルトが怪しい…という筋。

これは結局、**コア(FM音源エンジン)の外**の話だった。アプリ層のゲイン構成の問題で、M2DX-Core(音源そのもの)には関係ない。容疑としては挙がったけど「似てない」の本丸じゃないので、アプリ側のissueに切り分けてコアの調査に戻る。

音が変なとき、FX段の既定値みたいな"アプリ層"はいちばん最初に疑われるわりに、たいてい真犯人じゃない。でも潰さないと先に進めない。

## 3回目：ビット一致を証明した。engine無罪、のはず

ここで地道なことをやった。実際の `rom1a.syx`(DX7のROM1Aカートリッジのダンプ)から BASS1 のパッチ128バイトをそのままテストに埋め込んで、2つ確かめた。

1. パーサが SysEx を正しく展開するか
2. 展開したパッチをレンダリングした波形が、参照実装(dx7ref = Dexed由来のC実装)と一致するか

結果。

- パーサ: 全オペレータのパラメータ + グローバル設定(アルゴリズム / フィードバック / transpose)が、正規の展開と完全一致
- エンジン: ノート24〜96 × velocity40〜127 を **44.1kHz と 48kHz の両方**でレンダリング。**全部 dx7ref と0サンプルのズレ**。BASS1はアルゴリズム16・フィードバック7という濃いめのパッチだけど、それでもサンプル単位で一致した。

ピークも ≤0.24〜0.37(出力スケール /2^28)でクリップなし。

> 結論(3回目): パーサもエンジンもDEXEDとビット同一。「似てない」原因はエンジンの外。実機スピーカーの物理歪みか、聴感か、参照にしてるDexed側か。

証明したんだから、もう engine は無罪確定。…と思った。

*これがいちばん危なかった。*

## 4回目：実Dexedと比べたら、うちのほうが明るい

「engine無罪」を確定させる前に、念のため本物のDexedの音を録ってA/Bした。Logicで BASS1 を C4・vel127 で書き出して、M2DX、dx7ref、実Dexedの3つでcentroidの時間変化を測る。

vel127、こうなった。

| 音源 | アタックのcentroid | 700ms以降 |
|---|---|---|
| 実Dexed (Logic録音) | 2252Hz | ~125Hz |
| dx7ref (参照C実装) | 4540Hz | ~500Hz |
| M2DX (本番) | 4820Hz | ~700Hz |

*…あれ?*

実Dexedは700ms以降、モジュレータが減衰しきって倍音がほぼ消える(125Hz ≒ 基音だけの純正弦波)。ところがM2DXは700Hzで、**いちばん減衰が遅い**。うちのほうが長く明るく鳴ってる。「engineはDEXED忠実」がここで崩れた。

BASS1のモジュレータのエンベロープは、設計上レベルが0まで落ちて無音になるはず。なのに倍音が居残ってる。**EG(エンベロープ)の減衰が遅いんじゃないか**、と疑った。ビット一致の"相手"だった dx7ref ごと、明るすぎるんじゃないか、と。

> 結論(4回目): engineが怪しい。EGのrate→time変換が実Dexedより遅い。

ビット一致してても、その基準そのものがズレてたら意味がない。…という方向に傾いた。

## 5回目：EGの式は一致してた。撤回

DX7Envelopeの実装を、実Dexed(というかMSFAの `env.cc`)と1行ずつ突き合わせた。エンベロープのインクリメント式はこう。

```
inc = ... << (2 + LG_N + (qrate >> 2))   // LG_N = 6
```

…**完全に一致**してた。レート3が7なら減衰に177秒かかるけど、それは実Dexedも同じ。M2DXのEGは遅くない。「EGが遅い」は誤診。撤回。

じゃあ同じピッチ・同じEGで、なんでM2DXのほうが明るいのか。アタックのスペクトルを細かく見たら、実Dexedは第4倍音(~520Hz)から上を **急にロールオフ**してた。M2DXは第7〜12倍音まで素直に伸びてる。…この"急なロールオフ"、フィルタの匂いがする。

ここから真因が一気にほどけた。

## 真因①：transposeの掛け違い

そもそもピッチが違ってた。

BASS1は **transpose -12**(1オクターブ下げ)を持っていて、さらに OP1 が coarse 0(周波数0.5倍)。だから「C4を弾く」と、本物のDX7もM2DXも **C2(65.4Hz)** で鳴る。

ところが、相手のDexedの録音は transpose を適用してなくて **C3(130.8Hz)**。同じ音色のはずが、最初から1オクターブ違いをA/Bしてた。

*そりゃ似てないわ。* しかもこれ、M2DXのほうが仕様通り正しい。

## 真因②：ユーザーはDexedの「別エンジン」と比べてた

ピッチを合わせても、まだDexedのほうがM2DXより暗い。最初はCUTOFF(ローパスフィルタ)とLogicのEQで倍音が削れてるんだと思った。それも乗ってた。でも本丸はもっと手前にあった。

**Dexedには音を出すエンジンが複数ある。**

- **Modern (PM)**: さっきから延々ビット一致を取ってる、MSFAベースの高精度な位相変調エンジン。理論的に「正しいFM」。
- **Mark I**: 実機DX7の音源チップ **OPS(YM21280)** を模したモード。OPSは対数のsin+expをハードウェアでやってて、量子化が粗いぶん、Modernより **暗くて暖かい**。いわゆる「DX7の実機らしい音」はこっち。

ユーザーが「実機の音」として鳴らしてたDexedは、この **Mark I** だった。

つまり、こっちは延々「Modern(M2DX) vs Modern(Dexed)」でビット一致を確認してたのに、ユーザーは「Modern(M2DX) vs **Mark I**(Dexed)」を聞き比べてた。*そりゃ違う。* 別のエンジン同士なんだから。

念のため、M2DX-Coreのエンジンを各DSPコンポーネント(exp2ゲイン表2048点、sinテーブル2048点、FMカーネル、フィードバック)単位で canonical MSFA とサイドバイサイド照合する監査もかけた。全部ビット一致。M2DXのModernは「Dexed Modern」に対して完璧に忠実。**でもユーザーが欲しかったのはMark Iの音だった。**

## 真因③：OP5の"居残り"。でもパッチ通り

最後に残った疑問。「フィルタやエンジン差を抜きにしても、BASS1のsustainってそもそも明るくない?」 per-operator(オペレータ単位)でミュートして測った。

犯人は **OP5**(BASS1のアルゴリズム16で、キャリアOP1を変調する主モジュレータ)。OP5のエンベロープがこう。

```
OP5:  R1=99  R2=0  R3=0  R4=0     // レート(変化の速さ)
      L1=99  L2=0  L3=0  L4=0     // レベル
      OL=62                        // 出力レベル
```

L2以降が0だから、本来すぐ無音まで落ちる…はずが、レベルがR2の区間で止まって、**R2=0 + レートスケーリング = いちばん遅いインクリメント**になる。結果、2秒かけて内部ゲインが 0.84→0.55 とほとんど減らない(目標レベルに到達するのに約93秒かかる計算)。だからモジュレータが鳴り続けて、sustainが明るい。

ミュートA/Bで裏を取った。OP5を消すと、sustainのzero-cross(ゼロ交差 = 波形が0をまたぐ頻度、明るさの簡易指標)が **327Hz→131Hz**、約60%下がる(OP2が二次的に20%効いてた)。

で、これは **バグじゃない**。OP5のレートとレベルはROM1AのBASS1パッチにそう書いてある通りで、MSFAのコアもそう動く。実際、このゴールデン設定でM2DXをレンダリングすると、dx7refと **2秒の全区間(1378ブロック)でビット一致(ミスマッチ0)** する。

ここで3回目の伏線が回収される。最初の bit-exact テストは **200ブロック(290ms)までしか見てなかった**。アタックは一致してても、その先のsustainの居残りを見てなかった。テストの窓が短くて、いちばん問題になる定常部を見逃してた。

## 5回間違えて分かったこと

並べるとこう。

- **bit-exactの"相手"が正しいとは限らない**。dx7ref相手にサンプル一致してても、その dx7ref 自体が(実Dexedの Mark I より)明るかった。参照を疑うのが最後まで遅れた。
- **テストの窓が短いと定常部の乖離を見逃す**。290msまで緑でも、2秒見たら別の話だった。オーディオの回帰テストは、アタックだけじゃなくsustainまで伸ばさないと意味がない。
- **A/Bは条件を揃えてから**。transpose、エンジンモード、フィルタ、EQ。ひとつ違うだけで「似てない」は当たり前に出る。最初にこれを揃えてたら5回も迷わなかった。
- **"歪み"の主観は当てにならない**。実測したらクリップでもエイリアスでもなく、ただの正当なFM明度だった。

## 解決編：Mark I(OPS)エンジンを作り足した

ここまでで「M2DXのModernは正しい」は証明できた。でも、それは *ユーザーの困りごとを1ミリも解決してない*。「あなたの音は仕様通りです」と言われて嬉しい人はいない。聞きたい音が出ないなら、出せるようにするしかない。

というわけで、**Mark I(OPS)エンジンをM2DX-Coreに実装した**。

### Mark I Engine とは何か

ざっくり言うと、**実機DX7の音源チップ(OPS / YM21280)の挙動を再現するエンジン**。Modernとの違いはこう。

- **Modern (PM)**: MSFAベースの位相変調。高精度・クリーン。理論上の「正しいFM」。M2DXのデフォルト挙動はこれで、Dexed Modernにビット一致。
- **Mark I (OPS)**: 実機OPSチップの対数sin+exp演算を模す。量子化が粗く、変調のかかり方も実機的。結果として **暗く・暖かく・少し太い**。「DX7の実機らしい音」はこっち。

実装はクリーンルームでやった。DexedのMark Iエンジン(`EngineMkI.cpp`)は **GPLなので一切見ず**、公開仕様と自前の `PROVENANCE.md` だけを根拠にゼロから書いた(M2DX-CoreをMITで配るための線引き)。EGのレベルをMark Iの対数減衰に変換する `markIAtten` みたいな関数を足してある。Mark Iは極性が逆で、*値が大きいほど減衰が深い*(Modernのゲインの逆)。ここは何度かバグらせた。

品質の担保は前と同じ方法。Modern用に `dx7ref` というCの参照ツインを持ってるのと同じく、Mark I用に `dx7refmki` というツインも作って、**両エンジンともサンプル単位でビット一致を常時チェック**してる(201テスト全green)。エンジンを増やしても「参照と一致してるか」を機械で見張る仕組みは変えてない。

### Mark I Depth は何を設定するのか

OPSの「暖かさ」って、煎じ詰めると **前方変調(モジュレータがキャリアを変調する強さ)が実機だと少し弱まる**ことから来てる。なのでMark Iエンジンでは、前方変調を **÷X で低減**してOPSの音に寄せる。この **X** を動かすのが **Mark I Depth**。

- 範囲は **÷2.0 〜 ÷16.0**(0.1刻み)。内部的には固定小数点のスケール係数(`markIModScale`)で持ってる。
- **除数が大きいほど変調が弱まる → より暗く・暖かく**なる。小さいほどModern寄りの明るさに戻る。
- 出荷時のデフォルトは **÷5**。これは理屈で決めたんじゃなくて、**実機(と実機MIDI)を横に置いて耳で合わせた**結果、÷5がいちばん「あの音」に近かった。

```
Mark I Depth = 5.0   // ← デフォルト。実機を耳で聴いて決めた値
                     //    大きく(÷16)するほど暗く、小さく(÷2)するほど明るい
```

つまり「BASS1が似てない」と言われたあの音は、**Mark Iエンジン + Depth ÷5** で出せるようになった。最初の報告から、エンジンを1個生やすところまで来た。

## 「DX7忠実」とは何だったんだろう

最初に立てた問い。M2DXは何に"忠実"であろうとしてたのか。5回誤診して出た答えは、わりとシンプルだった。

**"DX7の音"は一枚岩じゃない。**

- MSFA/Dexed Modernに忠実な「理論的に正しいFM」(= M2DXのModern)
- OPSチップに忠実な「実機の暖かい音」(= M2DXのMark I)

このどっちも"DX7"で、人によって聞きたい方が違う。だから片方を選ぶんじゃなくて、**両方積んで切り替えられるようにした**のが結論。「Modernがビット一致してるから正しい」で押し切らず、Mark Iを作ったのは、たぶんそれが正解だった。

余談。「あなたの音は仕様通りです」で終わってたら、この記事は『正しさの自慢』で終わってた。テスターの耳のほうが、スペクトルの数字より先に正解(= 実機はもっと暗い)を知ってた、という話でもある。
