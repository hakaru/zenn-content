## 手元のRhodes、iPhoneに丸ごと入らないかな

**elepiano** というエレピ音源を作ってる。iPhone / iPad 単体で完結するスタンドアロンで、CoreMIDI で鍵盤を受けて RemoteIO で直接鳴らす。Rhodes Classic / LA Custom / Vintage Vibe EP / Wurlitzer 200A / ETI Roads MKII / C7 Grand の6音色と、Hammond B3（setBfree の物理モデリング）が入ってる。

同じ Rhodes を物理モデルでやってる **TineModeler4** も並行して作ってるんだけど、こっちは真逆のアプローチ。**実録サンプルを全部持っていく**方。

で、全部持っていくとこうなる。

```
$ du -ch data/*/.pcm_cache | tail -1
 34G	total
```

34GB。デコード済み PCM で。iPhone のストレージには入る。**でも RAM には入らない**。

この記事は、それをどうやって鳴らしてるかと、直近で「レイヤーを1本足したら眠ってたバグが3つ出てきた」話。

## 34GBをどう鳴らすか

素朴にやると2択になる。全部 RAM に載せる（無理）か、毎回ディスクから読む（初打鍵が遅れる）か。

採ったのは2層構成。

- **performance tier** — 各音色の代表 velocity を鍵ごとに1本ずつ、起動時に常駐させる。Rhodes Classic なら 85 鍵 + release 88 本で **199MiB**
- **dynamic streaming** — 残りは `mmap` して、打鍵で要求が来たページだけをローダースレッドが map する

打鍵すると、まず exact な record を streaming から取りに行く。まだ常駐してなければ **Miss を返して、代わりに performance tier の anchor を鳴らす**。要求はキューに積まれて、次の同じ鍵からは exact が鳴る。

つまり「初打鍵は必ず鳴る。ただし最初の1回だけは代表音」。無音にはしない。ここが一番こだわったところで、*サンプラーで最初の1音が鳴らないのは、楽器として終わってる*ので。

anchor と exact では録音レベルが違う（pp で +13〜21dB、ff で −8〜15dB ずれてた）ので、record ごとの onset RMS を index に持たせて、fallback したときだけゲインで段差を埋めてる。

## サンプルはどこから来るか

音源は Keyscape。ライセンスは持ってるので、**自分のライブラリから自分の端末用に**取り出してる（当然リポジトリにもアプリにも同梱しない）。

`.db` は独自コンテナで、XML のファイルテーブルの後ろに実データが並んでる。中身は FLAC を軽く包んだ形式で、ヘッダを差し替えて所定の変換をかけると普通の FLAC として読める。ここの具体的な手順は伏せる。

この抽出でだいぶ嵌まった。デコードしたはずのサンプルが、ときどき末尾 4096 フレームだけ欠ける。1000本に1〜2本。

原因は自分で書いた「CRC を直す」関数だった。圧縮データの中にたまたま現れる**偽の sync ワード**を次フレームの先頭と誤認して、実データの上に CRC を書き込んでいた。CRC-8 が一致してフレーム番号も連番になってる偽 sync が、1000本に1〜2本ある。

しかもこの関数、そもそも要らなかった。復号規則を正しく突き止めた時点で CRC は元から合っていて、131行まるごと消した。

*デバッグしてたつもりが、自分で埋めた地雷を掘り返してただけ…*

## 本題: メカ音を1本足す

Rhodes には打鍵と離鍵の**機械音**が別レイヤーで収録されてる。ハンマーと鍵盤が動く音。基音を持たないノイズで、これを attack / release に重ねると一気に「実機」になる。

`.db` を数え直したら、wav 7,637本のうち鳴らしてたのは 3,375本（44%）だけだった。残り **4,262本 / 297MiB が未使用**。その中にメカ音が入ってた。

打鍵メカ音 1,408本、離鍵メカ音 1,056本。CC27 に "Key Noise" を割り当てて鳴らすことにした。

設計で悩んだのは離鍵の方。**サステインペダルを踏んだまま鍵を離したら、メカ音は鳴るのか。**

実機は鳴る。ダンパーが下りないだけで、鍵盤機構は動くから。なので release サンプルの遅延処理からは完全に切り離して、`_note_off` の入口・`sustained` 判定より前でフックした。

あとメカ音は 128本の voice プールを共有するけど、**音楽的な voice は絶対に奪わせない**。空きがなければ諦める。逆に打鍵側は最初に mech を回収する。ノイズのために音符を切るのは本末転倒なので。

実装してテストを通して、実機に入れた。

……鳴らない。

## 「効いているか分からない」の正体

ここで手が止まった。Key Noise を上げても下げても違いが分からない。**そもそもソースがロードされてないのか、鳴ってるけど小さいのか、判断する材料がない**。

コードは何度読んでも正しい。CC の経路も追った。テストも通ってる。

なので、まず**数字が出るようにした**。Diag 画面に1行足す。

```
Key noise    <鳴った数> / <ソースがあって試行した数>
```

読み方はこう。

- `0 / 0` … ソースが載ってない
- `0 / N` … ソースはあるが acquire が Miss してる
- `N / N` … 鳴ってる

実機に入れて、Rhodes を数音弾いて、Diag を開いた。

```
Note On       49 / 49
Key noise      0 / 98
```

`0 / 98`。**ソースは載ってる。打鍵49 + 離鍵49 = 98回ちゃんと呼ばれてる。でも一度も鳴っていない。**

ここから先は一直線だった。

## 出てきたバグ3つ

### 1. ローダーがメカ音を無視していた

streaming の要求はキューに積まれる。それを処理する timer を見たら、こうなってた。

```cpp
processed = serviceAttack();
if (processed == 0) processed = serviceRelease();
```

`attack` と `release` しかない。**performance tier を持たないソースは、要求を積むだけで誰も処理しない**。永久に Ready にならない。

そして同じリストに `pedal_down` も入ってなかった。C7 Grand のペダル踏み込み実収録。こっちは「常駐してなければ通常の attack へ落とす」設計なので、**壊れてても無音にならない**。だから誰も気づいてなかった。

しかも Pedal Down を足したのは**同じ日の未明**。*一度も鳴らないまま実機に載って、そのまま気づかず1日過ごしてた…*

### 2. メモリ圧でも止まっていなかった

メモリ警告が来ると dynamic tier を止めてページを退避する。その関数がこれ。

```cpp
size_t disable_dynamic_tier_and_evict(StreamCache& cache,
                                      StreamingSampleDB* attack,
                                      StreamingSampleDB* release)
```

また同じ形。attack と release しか止めないのに、**共有キャッシュのページは全部退避する**。止め漏らしたソースは直後にページを引き戻すので、メモリ解放が丸ごと打ち消される。

2回続けて「手で並べた一覧への足し忘れ」だったので、列挙自体をやめて1箇所に寄せた。

### 3. 連打でマシンガン効果

鳴るようになった。実機で弾いてもらった。返ってきた感想。

> マシンガン効果　気になる

メカ音は round robin が4本ずつある。同じ打鍵でも毎回違うテイクが鳴るべきなんだけど、descriptor を選ぶ関数が **同じ velocity 範囲に並ぶ先頭を常に返していた**。連打すると完全に同じ波形が position 0 から重なる。

仕様書では「round robin は `acquire` の interface 変更が要るので今回は非目標」と書いてた。**これが間違いだった。** 選択関数の中でグループ内をカウンタで回すだけで済む。interface は1バイトも変えなくていい。

直したら副次効果が大きかった。release 系3セットは**全 round robin が既に端末に入っていて、3/4 が到達不能のまま死んでいた**。185MiB。追加転送ゼロでそのまま生き返った。

## おまけ: Drive が歪みすぎる

同じ日に別件。「Drive がちょっと歪みすぎる」と言われて中を見たら、サチュレーションの伝達関数がこうなってた。

```cpp
if (x < 1.5f)
    return x - 0.148f * x * x * x;
else
    return 1.17f;               // ← ここ
```

`x - 0.148x³` は x = 1.5 でちょうど頂点 **1.0005** に達する。なのに、そこから先を **1.17** で返してる。

```
in = 1.4999 → 1.0005
in = 1.5000 → 1.1700   +0.17 跳ぶ
```

ソフトクリップのはずが階段になってた。信号が 1.5 を跨いだ瞬間に高次倍音が一気に出る。

もう1つ、CC に対するカーブが線形（`1 + 7v`）で急すぎた。Rhodes は単音 ff のピークが 0.7 くらいあるので、**CC35 の時点で既に歪み域**に入る。CC 0〜35 がクリーンで、35〜127 が全部歪み。上の方はほぼファズ。*「微妙なオーバードライブ」を追い込む余地が構造的に無かった*。

二乗カーブにして ff が歪み始めるのを CC67 まで動かした。

| 歪み始める入力振幅 | CC32 | CC48 | CC64 | CC80 | ff が歪む |
|---|---|---|---|---|---|
| 修正前 `1+7v` | 0.73 | 0.58 | 0.48 | 0.41 | CC35 |
| 修正後 `1+7v²` | 1.18 | 0.94 | 0.73 | 0.56 | CC67 |

上端（19.8倍 / 25.9dB）は据え置きなので、激しい音は失ってない。

## 学んだこと

**音がしないとき、まず数字が出るようにする。**

コードを読み直した時間より、Diag に1行足して `0 / 98` を見た瞬間の方が情報量が多かった。しかもその1行が、2つ目・3つ目のバグまで芋づるで引っ張り出した。Pedal Down が黙って壊れてたのも、それがなければ見つかってない。

もう1つ。**「手で並べた一覧」は必ず足し忘れる。** 今回2回やった。3回目をやらないために、ソースの列挙は1箇所に寄せた。

あと `1.17f` みたいな**説明のないマジックナンバーは疑う**。多項式の頂点は係数から計算できるので、定数を書かずに式で持たせた。同じズレはもう起きない。

---

サンプル本体は配布できないので、鳴らすには自分のライブラリから作る必要がある。エンジン側は C++ で書いてて、iOS 版と旧 Raspberry Pi 版で同じコアを共有してる（Pi 版は凍結中）。

物理モデルの方（TineModeler4）とは、同じ楽器に真逆から迫ってる感じで、両方やってると気づくことが多い。サンプルは「その録音の一瞬」しか持ってなくて、物理モデルは「弾き方の連続」を持ってる。メカ音レイヤーみたいな、モデル化が面倒な部分はサンプルが圧倒的に強い。
