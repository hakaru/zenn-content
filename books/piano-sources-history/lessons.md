5世代を通じて学んだことを、技術ではなく **態度・方法論** の観点で並べる。

## 開発パターンの観察

### 「動かす → 整える」の徹底

どのプロジェクトも、まず最小構成で動かしてから整える順序を守っている。

- elepiano: 3月1日の最初のコミットで「PiSound MIDI synth engine」を動かしている。ハイブリッド・オルガン・FX・BLE・iOS はその後。
- TineModeler: v0.1.0 で「とりあえず音が出る」を達成、v0.8.0 までの 8 マイナーバージョンで磨いた。
- TineModeler3: v1.0 で機能完成、v1.x で品質・RT 堅牢性、というロードマップ。

完璧な設計から始めない。骨格は最初から見えている。

### リポジトリの分割タイミング

- 物理モデル（`PhysicalModel/`）は iRhodes 内のサブディレクトリで始まり、研究比重が増した時点で TineModeler として独立
- DDSP 残差学習は TineModeler の `ddsp/` から始まり、本格化した時点で TineModeler2 として独立
- 製品化のタイミングで TineModeler3 が独立
- RT 修正は TineModeler3-followups という worktree で並列管理

**「コードベースが特定の技術課題に支配されはじめたら、分離する」** という判断基準が一貫している。

### ドキュメントを「開発の副産物」として書く

elepiano の `ClaudeWorklog202603*.md` は対話の整理。TineModeler の `CHANGELOG.md` は都度書き留め。TineModeler3 の `AGENTS.md` は memory context。

事後にまとめて書くんじゃなくて、**開発のフローの一部としてドキュメントを生成する**。これが今回の「経緯のドキュメント化」（≒ この本）にも効いてる。

### エージェント駆動開発の活用

TineModeler3 の `AGENTS.md` には:

- Codex / Gemini 並列レビュー + Claude Code 統合化
- 高コスト検証は並列実行
- 見解が割れた場合は実コード確認で決着

という運用ルールがある。複数 LLM の意見を独立に得て、対立を物理コードで決着する、というメタ手法。

156 commits / 5日 や 86 commits / 10日 の速度感は、エージェント並走の副産物。

## 反省

### 1. 聴感評価の不足

これが一番大きい。

全プロジェクトを通じて **客観指標（Mel-L2, val_loss, CPU%, レイテンシ）** は丹念に取った。でも **主観指標（MOS スコア、A/B テスト）** はほぼ未整備。

TineModeler2 の課題リストにも「聴感評価（MOS）未実施」と明記されている。製品化フェーズで「数値はいいが、買ったお客さんが満足するか」を測る仕組みが弱い。

*次にこの規模のプロジェクトをやるなら、最初から A/B テストハーネスを組み込む。*

### 2. データセット拡張の遅れ

DDSP 学習データは Rhodes Classic のみ（1,615 FLAC）。LA Custom、Vintage Vibe、Wurlitzer など他機種への拡張は **「コスト ¥2,000 程度で可能」と試算されているけど未着手**。

機種ごとに物理モデルを再学習させると、製品ラインを広げられる（RhoDex Classic / RhoDex LA / RhoDex Wurlitzer …）。研究投資の小ささに対してリターンが大きそうな領域。

### 3. マーケティング・ストア出荷の未準備

TineModeler3 で「機能完成 100%」「テスト 67/67」「RT 安全性修正完了」まで来ているのに、**App Store 提出（codesign / entitlements / sandbox 整備）が残っている**。

技術的な完成度が高くても出荷できなければ意味がない。最後の 1 マイル（プロダクト化）の準備工数を最初に見積もるべきだった。

### 4. iOS / macOS / DAW で同じことを 3 回作っている

elepiano（Pi）→ iRhodes（iOS）→ TineModeler3（macOS / iOS）と、似たエンジンを 3 回作っている。`SpscQueue` や `biquad` は共通だけど、上層は毎回作り直し。

「Core C++ ライブラリ + プラットフォーム別シェル」という構造を最初から強制すれば、移植コストは下がっただろう。

**ただし**、移植のたびに学びがあって、それが次世代に活きている側面もある。NAM の手書き化、IR Convolver の Accelerate 化、HybridVoice、`paramSerialQueue`、Voice 単位 MLState — どれも「移植の過程で発見された」もの。一概に非効率とは言えない。

### 5. legal / IP の慎重さ

elepiano では Keyscape の SpCA フォーマットを逆エンジニアリングして使った。技術的には素晴らしい成果だけど、商用配布する場合は法務リスクがある。

iRhodes 以降では物理モデル + DDSP（自前学習データ）に振り切り、サンプルを完全に外している。**結果的に正しい判断**だった。

逆エンジニアリングを「**技術的好奇心の対象**」と「**プロダクトの依存先**」で切り分ける、というのは大事。前者はやってよし、後者はやめておけ。

## 次のシリーズがあるとしたら

### 技術観点

1. **マルチ機種展開**: LA Custom、Wurlitzer、Vintage Vibe を学習データセット化
2. **温度・経年シミュレーション**: パラメータの時間変化（部屋の温度、何時間演奏したか）
3. **Cabinet IR / Speaker emulation**: 実機録音のキャビネット特性を IR で
4. **MPE / Polyphonic aftertouch の活用**: 物理モデルとの相性が良い
5. **クラウド学習基盤の常設化**: ユーザー録音から差分を学習する preset community

### プロセス観点

1. **A/B テストハーネスを最初から組む**
2. **製品化チェックリスト（codesign / sandbox / 法務）を 0 日目に作る**
3. **Core ライブラリ / Platform シェル分離を最初から強制する**
4. **聴感評価担当（自分以外の耳）を確保する**

特に最後のが効きそう。**自分の耳だけだと、自分の作ったものを過大評価する**バイアスから逃げられない。

## 結論

このシリーズは、技術的には「物理 × ML ハイブリッド楽器音源の有効性を **5回の実装で証明した**」と総括できる。

残るのは、それを **実際に売れる形で世に出すこと**。

これ以上技術検証を重ねても得るものは小さい。App Store 提出 → リリース → ユーザーフィードバック という、これまで触っていない領域に進む段階。

…そういうわけで、もしこの本を読んで「で、製品はどこで買えるの？」と思った人は、もう少しだけ待ってほしい。
