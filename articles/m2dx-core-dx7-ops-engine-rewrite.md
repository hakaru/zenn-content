DX7の音をSwiftで作り直して、MSFA(Dexedの心臓部)とサンプル単位でビット一致するところまで持っていった。「DX7の音、完全に再現できた」と思ってた。

…のに、いくつかのプリセットの音が、どうも実機と違う。BASS1とか、E.PIANOとか。*気に入らない。*

で、原因をさんざん追いかけた末に出た結論が、わりとしんどかった。**MSFAにこだわってたのが、そもそも間違った方向だった。** bit-exactを突き詰めるほど、実機のDX7から遠ざかってた。

だからエンジンを一から書き直した。この記事はその話。新しいエンジンの中身と、チューニングの仕方と、ついでに作ったTX816シミュレーションまで。

## 結論

先に何をやったか。

- M2DXのエンジンは、MSFA(= Dexedの「Modern」モード)にビット一致してた。これは「理論的に正しいFM」。**でも実機DX7初期型の音じゃなかった。**
- 実機初期型の音は、音源チップ **OPS(YM21280)** が作ってる。MSFAの「きれいなFM」とは別物。粗くて、暗くて、暖かい。
- なので **OPSを再現する2個目のエンジン「Mark I」を一から書いた**。位相変調じゃなく、対数領域の log-sine + exp。前方変調を絞って実機の暖かさに寄せる。
- 暖かさの量は **Mark I Depth**(÷2〜16)で可変。BASS1とE.PIANOをDexedの Mark I 相手に耳とスペクトルで校正して、出荷は ÷5。
- ついでに **TX816**(DX7を8台積んだ伝説のラック音源)のレイヤーも実装した。最大8レイヤー、デチューン/パン/ランダムで分厚くする。

「MSFAを移植すればDX7の音」と思って始めたのに、結局OPSエンジンを別に書くことになった。順番に書く。

## MSFAにこだわってた、という間違い

前に「[DX7をSwiftで再実装した話](https://zenn.dev/hakaru/articles/m2dx-core-dx7-fm-synth-swift)」という記事を書いた。要点はこう。DexedとMSFA(Google製のDX7互換FMエンジン)のコードを読んで、Swiftで作り直して、**MSFA/dx7refとサンプル単位でビット一致**させた。テストでサンプル0個ズレを保証してる。「DX7の音が出る」の証明だ、と。

ところが、実際にいくつかのプリセットを鳴らすと、実機(と、みんなが実機の音だと思ってるDexed)と違う。特にBASS1。明るすぎる。

最初は自分のバグを疑った。クリップ? エイリアス? FX? エンベロープの減衰が遅い? …全部潰した。エンジンはMSFAにビット一致してて、どこも間違ってない。(この迷走は5回くらい結論がひっくり返って、それだけで記事一本書けるんだけど、ここでは結論だけ。)

行き着いた答えはこう。**ユーザーが「実機の音」として聴いてたのは、Dexedの「Mark I」エンジンだった。** Dexedには音を出すエンジンが複数ある。

- **Modern (PM)**: MSFAベースの位相変調。高精度でクリーン。理論的に正しいFM。**M2DXがビット一致させてたのはこっち。**
- **Mark I**: 実機DX7初期型の音源チップ **OPS** を模したモード。粗くて暗くて暖かい。**みんなが「DX7の音」と思ってるのはこっち。**

つまり、こっちは「Modern vs Modern」でビット一致を喜んでたのに、実機の音は「Mark I」のほうにあった。bit-exactを突き詰めれば突き詰めるほど、MSFAの「きれいすぎるFM」に近づいて、実機OPSの「いい感じに粗い音」から離れていく。**こだわる方向を間違えてた。**

## OPSチップって何が違うのか

実機DX7初期型(Mark I)の音を作ってるのは、**OPS(YM21280)** という音源LSI。この中身は、Ken Shirriff がチップのダイ写真(回路を顕微鏡で撮ったやつ)から解析して公開してる。

ざっくり、MSFA(Modern)とOPS(Mark I)はFMの計算のやり方が違う。

- **Modern**: 位相変調。サインテーブルを引いて、指数のゲインを掛ける。`sinLookup(phase + input)` に `exp2(level)` を掛ける、みたいな素直な演算。
- **OPS / Mark I**: 全部 **対数領域** でやる。サインも対数で持って(log-sine)、変調も減衰も対数の足し算で重ねて、最後に一回だけ exp で戻す。途中の量子化が粗いぶん、倍音の出方とサステインの暗さに「実機のクセ」が出る。

この「対数でやる」「粗い」が暖かさの正体。Modernのきれいなサインじゃ出ない。だから **演算そのものを書き直す** しかなかった。

## エンジンを一から書く

新エンジンを `Mark I` として足した。エンジンは2択になる。

```swift
public enum FMEngine: UInt8, Sendable, CaseIterable {
    case modern = 0   // MSFA / 位相変調。クリーンで明るい
    case markI  = 1   // OPS / log-sine+exp。粗くて暖かい
}
```

レンダリングはブロック単位でこう分岐する。

```swift
if engineMode == .modern {
    renderBlockModern(...)   // 従来のMSFA経路
} else {
    renderBlockMarkI(...)    // OPS経路
}
```

中身で効いてるのは2つ。**対数減衰** と **前方変調の絞り**。

### 対数減衰 (markIAtten)

Modernはエンベロープのレベルを `exp2` でゲインに変える(大きいレベル = 大きい音)。OPSは逆で、**対数の減衰量** として扱う。コードはこれだけ。

```swift
func markIAtten(_ levelIn: Int32) -> UInt16 {
    let raw = kMarkIEnvMax &- (levelIn >> 14)   // kMarkIEnvMax = 1<<14 = 16384
    let clamped = max(0, min(kMarkIEnvMax, raw))
    return clamped == 0 ? UInt16(kMarkIEnvMax - 1) : UInt16(clamped)
}
```

ポイントは極性が逆なこと。**値が大きいほど深く減衰(= 静か)**。Modernのゲインとちょうど裏返し。ここを何度か取り違えてバグらせた。*いや、向き逆なんだって…* と毎回なる。

### 前方変調の絞り (markIModScale)

OPSの暖かさは、煎じ詰めると **モジュレータがキャリアを変調する強さが、実機だと少し弱まる** ことから来てる。なので前方変調だけを `÷X` で絞る。

```swift
var markIModScaleQ12: Int32 = 512   // Q12固定小数点。512/4096 = ÷8

func markIModScale(_ v: Int32) -> Int32 {
    Int32(truncatingIfNeeded: (Int64(v) &* Int64(markIModScaleQ12)) >> 12)
}
```

Q12(分子4096)の固定小数点で持ってて、`512 = ÷8` がデフォルト。これは後述のビット一致テストの基準値でもある。**絞るのは前方変調だけ** で、キャリアのDAC出力とフィードバック経路はそのまま(OPSもフィードバックは別扱い)。

### クリーンルームで書く

ここ、ライセンス的に気をつけた。DexedのMark Iエンジン(`EngineMkI.cpp`)は **GPLなので一切見てない**。根拠にしたのは公開情報だけ。

- Ken Shirriff のOPSチップ ダイ写真リバースエンジニアリング
- OPL3(別のYamaha FMチップ)の数学ドキュメント
- Yamaha のDX7サービスマニュアル/技術資料

これを `DX7MarkI_PROVENANCE.md` に「どこを見たか」として残してある。M2DX-CoreをMITで配るための線引き。前のModernエンジンでMSFA(Apache 2.0)を扱ったときと同じ作法。

### 参照ツインで品質を見張る

Modern用に `dx7ref`(C実装)というビット一致の相手を持ってるのと同じく、Mark I用にも `dx7refmki`(Apache 2.0のC実装)を書いた。で、**両方をサンプル単位で突き合わせるテストを201個** 回してる(5アルゴリズム×3ノート×3ベロシティ×200ブロック、0サンプルズレ)。

エンジンを増やしても「参照と一致してるか機械で見張る」やり方は変えない。前回「参照そのものが間違ってたら意味ない」と痛い目を見たので、Mark Iの参照は **die-shotベースのOPS再現** という、MSFAとは別系統を立てた。

## チューニング：Mark I Depth

「暖かさ」は前述の前方変調の `÷X`。これをそのまま **Mark I Depth** スライダーに出した。

- 範囲 **÷2.0 〜 ÷16.0**、0.1刻み
- **除数が大きいほど暗く・暖かく**(変調が弱まる)、小さいほどModern寄りの明るさ
- エンジン内部のデフォルトは **÷8**(ビット一致テストの基準値)
- アプリの出荷値は **÷5**

```swift
public var markIDivisor: Double = 5.0 {   // 出荷デフォルト
    didSet {
        synth.setMarkIModDivisor(markIDivisor)
        UserDefaults.standard.set(markIDivisor, forKey: "M2DX.markIDivisor")
    }
}
public static let markIDivisorRange = 2.0...16.0
```

この ÷5 は理屈で決めたんじゃない。**BASS1とE.PIANO1を、Dexedの Mark I を相手に、耳とスペクトル分析で合わせた** 結果。コミットメッセージに「a fixed engine trait, not a per-patch fudge(エンジン固有の特性であって、パッチごとのごまかしじゃない)」と書いてる。1音だけ合わせると他が崩れるので、複数パッチで破綻しない ÷5 に落とした。

校正が効いてるかはテストで固定してる。BASS1のサステインのスペクトル重心(明るさの指標)が、

```
Modern : 685 Hz
Mark I : 176 Hz   → ratio 0.26
```

Mark Iで明るさが **26%まで落ちる**。実機の暗いサステインに近い。このテストは最初 `withKnownIssue`(未達でも通す)にしてたのを、校正後に **ハードアサーション**(下回らなきゃ失敗)に昇格させた。「暗くなってること」を仕様として固定した、ということ。

## ついでにTX816も

DX7初期型の音が出るようになると、次に欲しくなるのが **TX816** の音。TX816は、DX7相当の音源モジュール(TF1)を **8枚** ラックに積んだ、80年代の伝説的な音源。8台をちょっとずつデチューンして重ねると、あの分厚いブラスやベースになる。

エンジンが1ボイス出せるなら、レイヤーは構成の問題。`layer` モードを足して、128ボイスのプールを複数スロットに配った。

```swift
// P parts × U unison を一発で設定
setLayerPartition(parts: 8, unison: 1, detuneCents: ...)
```

パーティションは4種類。

| 構成 | 中身 | 用途 |
|---|---|---|
| 8×1 | 8レイヤー、ユニゾンなし | フルTX816(各スロット別パッチ) |
| 4×2 | 4パート×2ユニゾン | 厚めの4音色 |
| 2×4 | 2パート×4ユニゾン | 2音色を太く |
| 1×8 | 1パッチ8ユニゾン | モノシンセを極太に |

各スロットは個別に持てる。

```swift
struct LayerSlot {
    var patch: DX7Preset    // スロットごとに別パッチ
    var levelDb: Double      // 音量
    var pan: Double          // 定位(equal-power pan)
    var panRandom: Bool?     // ランダムパン
}
// 全体: detuneCents(1〜150c), detuneMode(0=均等 / 1=ランダム)
```

デチューンは「均等にずらす」か「ランダムにばらす」か選べる(実機の個体差っぽさはランダムが近い)。パンも equal-power で、ランダム配置もできる。プリセットはJSONでDocumentsに保存(`TX816Presets/*.json`)。

*8台ぶんのDX7が手のひらで鳴るの、わりと壮観です。*

## で、「DX7忠実」って何だったんだろう

最初の話に戻る。MSFAをビット一致させて「DX7の音ができた」と思ってた。でもそれは **MSFA(Modern)に対して** 正しかっただけで、実機DX7初期型はそこにいなかった。

**MSFAを移植すればDX7の音、という出発点が、半分しか合ってなかった。**

だから今は2エンジン積んでる。

- **Modern** — MSFA/Dexed Modernにビット一致。理論的に正しい、クリーンなFM
- **Mark I** — OPS(YM21280)再現。実機初期型の、粗くて暖かい音

このどっちも"DX7"で、人によって(曲によって)欲しい方が違う。片方を「正しい」と決めずに、両方出して切り替えられるようにした。MSFAで作るはずがOPSエンジンまで書く羽目になったけど、たぶんこれが正解だった。

…そもそも「実機の音と違う」と最初に言ったテスターの耳が、スペクトルの数字より先に正解を知ってた、という話でもある。

## 追記：その後もDX7を追いかけてる

この記事を書いたあとも、実機に寄せる作業は続いてる。ざっと最近の分を。

### Mark IのDACまで12-bitにした

OPSの暖かさは log-sine+exp の演算だけじゃなくて、**出力のDAC**にもある。実機初期型はキャリア出力を**指数付きの12-bit DAC**で吐いてて、小さい音ほど量子化が粗い。この「12-bit companding」をMark Iに足した。

最初、正規化して全ボイスを足したあとのミックスに掛けてたら、ピークが小さすぎて(全体で ~0.08)指数が常に最大に張り付いて、**ただの固定量子化 = まったく効いてない**状態になってた。*一回まるごとバグらせた。* 直して、**ボイスごとに生のOPSサンプルに**掛けるようにしたら、音量依存の量子化がちゃんと効くようになった。Settingsの「Vintage 12-bit DAC」トグルでオン/オフできる(オフはビット完全一致を維持するので、参照ツインとのパリティは無傷)。

### bit-exactの「外側」の忠実度も監査した

Mark Iを足したあとで、Modern側も含めて**実機DX7 / Dexedと突き合わせるfidelity監査**をやった。bit-exactの内側じゃなく、その外の「パラメータの解釈」がズレてないか、という観点。で、いくつか直した。

- **キーボードレベルスケーリング(KLS)** — ブレークポイント左右のレベル減衰カーブがDexedの ScaleLevel/ScaleCurve と合ってなかった
- **オペレータのデチューン** — DEXEDは detune を「音程依存の量」で掛けてた(低音ほど深い)。固定±centsじゃなかった
- **Pitch EG / LFO** — Pitch EGの非線形テーブル、LFOの速度テーブル(MSFAの式じゃなく、Dexedの100エントリのテーブルが正だった)
- **EG bias** — ブレス/AT/ホイール/フットからオペレータレベルへのバイアス経路

「参照そのものが実機と違ったら意味ない」の教訓の続きで、今回はDexedの**実ソースをcurlで引いて**突き合わせた。*監査レポート側の引用が間違ってた箇所すらあった。*

### DAWから全パラメータをオートメーションできるようにした

AUv3としてLogic/GarageBandに載せたとき、FXとマスターボリューム以外の**約163個のsynth param**はホストオートメーションが効かなかった。パラメータ設定が「メインスレッドのSPSC producer」で、レンダースレッドから叩くと**マルチプロデューサ違反**になるから。

これを**MIDI 2.0のNRPN経由**で解決した。ホストのオートメーションをNRPNに変換して、既存のロックフリー `sendMIDI` リング(AUv3内では producer==consumer==render で安全)に流し、`render()` の中で `currentSnapshot` を**audio-localに**書き換える。メインスレッド側の `shadowSnapshot` には一切触らない。これで operator level/ratio/detune/EG/KLS・LFO・Pitch EG・コントローラまで、DAWのオートメーションレーンで動くようになった。仕上げに敵対的レビュー(Claude数体 + Codex)を通して、feedbackのマッピング漏れと no-opイベントで無駄にapplyが走る件、low-severityを2件潰した。
